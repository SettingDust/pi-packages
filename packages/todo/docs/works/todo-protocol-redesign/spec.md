## 1. Accepted Baseline Boundary and Model

Exactly four provider-visible tools exist: `todo_set`, `todo_add`, `todo_transition`, and `todo_view`. One coordinator owns validation, committed state, invocation-order serialization, projections, and results. The canonical snapshot is exactly `{tasks}`. A task group is exactly `{name,todos}`. A todo is exactly `{name,description,status}`. All objects use `additionalProperties:false`.

Names and descriptions must be trimmed non-empty strings. Matching is exact and case-sensitive. Task names are globally unique and todo names are unique within a task. Status is exactly one of `pending`, `in_progress`, `completed`, `cancelled`. New todos are always `pending`. Multiple task groups may contain `in_progress` todos simultaneously; each group remains represented in `tasks` and no single active summary is selected or derived.

**Unaccepted T0 presentation-anchor amendment candidate (not authority):** For presentation only, a consumer may derive a deterministic read-only anchor from existing canonical task and todo order. This creates no canonical primary, selected, or unique active todo; does not mutate, serialize, persist, write back, or feed business logic; does not compress or replace active groups; and introduces no priority, timestamp, hidden selection, or fallback state. Every group containing `in_progress` todos remains independently represented, and the prohibition on a canonical or protocol single-active summary remains in force. This candidate changes no request, result, schema, canonical state, restore, queueing, persistence, tool behavior, complete-removal authority, implementation boundary, or other protocol contract.

## 2. Exact Request Schemas

JSON Schema draft 2020-12 applies. These are the complete request contracts; every listed object has `additionalProperties:false` and every omitted property is rejected. `minItems` is normative.

```json
{"type":"object","additionalProperties":false,"required":["tasks"],"properties":{"tasks":{"type":"array","minItems":0,"items":{"type":"object","additionalProperties":false,"required":["name","todos"],"properties":{"name":{"type":"string"},"todos":{"type":"array","minItems":0,"items":{"type":"object","additionalProperties":false,"required":["name","description"],"properties":{"name":{"type":"string"},"description":{"type":"string"}}}}}}}}}
```

`todo_set` accepts only `{tasks}`. It replaces the complete state; each creation item is exactly `{name,description}` and produces status `pending`. It does not accept `status` or `initialTransitions`.

```json
{"type":"object","additionalProperties":false,"required":["task","todos"],"properties":{"task":{"type":"string"},"todos":{"type":"array","minItems":1,"items":{"type":"object","additionalProperties":false,"required":["name","description"],"properties":{"name":{"type":"string"},"description":{"type":"string"}}}}}}
```

`todo_add` accepts only `{task,todos}`. `task` must be a trimmed non-empty name matched exactly and case-sensitively. If that task exists, the operation must append the supplied todos in request order after its existing todos, including when the task is empty. Otherwise it must create exactly one task `{name:task,todos}` at the end of the task list with the supplied todos in request order. Every supplied todo must be exactly `{name,description}` and become `pending`; `todos` must contain at least one item. Both branches must preserve all existing task order, todo order, names, descriptions, and statuses. Duplicate todo names within the request or against the existing target must fail atomically; the same todo name in distinct tasks is valid. No trimming, case folding, fuzzy matching, rename, replacement, or status reset is permitted by `todo_add`. Section 10 defines compatibility and verification consequences.

```json
{"type":"object","additionalProperties":false,"required":["transitions"],"properties":{"transitions":{"type":"array","minItems":1,"items":{"type":"object","additionalProperties":false,"required":["task","todo","status"],"properties":{"task":{"type":"string"},"todo":{"type":"string"},"status":{"type":"string","enum":["pending","in_progress","completed","cancelled"]}}}}}}
```

`todo_transition` accepts only `{transitions}`. Every transition item is exactly `{task,todo,status}`. Every target task and todo must already exist; a missing target must fail atomically and must not create a task or todo. Duplicate transition targets are rejected. Unknown input is rejected by the strict schema.

```json
{"type":"object","additionalProperties":false,"required":[],"properties":{}}
```

`todo_view` accepts only `{}` and never mutates or writes persistence. Runtime invariants include trimmed non-empty values, uniqueness, exact case-sensitive task lookup (create-if-missing for `todo_add`, existing targets required for `todo_transition`), duplicate transition targets, atomicity, queue ordering, preservation of each group's todo statuses, and restore classification.

## 3. Results, Errors, Queue, and Atomicity

Success is exactly `{result,snapshot}`, with result `set`, `add`, `transition`, or `view`. Failure is exactly `{result:"error",error:{code,message}}`; error messages must not expose payload values. Invalid request, duplicate names, missing transition task/todo, and duplicate transition target are rejected according to the documented precedence and transition/source order. An absent `todo_add` task alone must not produce `not_found`; it must take the creation branch after validation. For `todo_add`, validation must retain current-state validation before strict request parsing, request-item validation in source order and request duplicate checks before target collision checks, then candidate invariant checks before publication. Invalid shape/text or empty `todos` must remain `invalid_request`; duplicate todo names must remain `duplicate`, with non-payload messages.

The coordinator serializes mutations in invocation order, validates current state, builds a complete candidate, checks runtime invariants, atomically replaces committed state, updates widget/reminder/formatter projections, then returns. A failed mutation changes neither state nor projections. Failure must not prevent later queued operations from running against the last committed state. `todo_add` must resolve existence against the committed state when its queued operation executes. Two queued adds for the same initially absent exact task with distinct todo names must create then append in invocation order, producing one task, not duplicate tasks. If the later add collides with a todo committed by the earlier add, only the later operation must fail. No package-owned persistence operation occurs before or after publication.

## 4. Restore and Accepted Host Boundary

Only a successful complete canonical Todo `toolResult` already present in the current session branch is a branch-local restore checkpoint. A successful `todo_add` in either branch must return the same `{result:"add",snapshot:{tasks}}` complete-state result; when recorded by the Host as an eligible checkpoint, it must restore all tasks, todos, order, and statuses, including the newly created task. No request, result, canonical snapshot, or persistence schema change is introduced by create-if-missing. `execute` return is not append or persistence acknowledgement. Restore scans current branch records, newest completion sequence first, then nearest ancestors; ties use physical position. Invalid, incomplete, failed, wrong-tool, wrong-version, and malformed records are skipped with one non-payload diagnostic per candidate; no valid record yields `{tasks:[]}`.

Host checkpoint evidence is pinned only to the directly inspected `@earendil-works/pi-coding-agent` 0.84.2 files and establishes the Host branch boundary only. It does not claim pi-agent-core loaded-byte, runtime-loaded-core-module, or future-version identity.

## 5. Legacy Restore

Legacy parsing occurs only after canonical discrimination fails and the root is unambiguously legacy. Strict root shape is `{phases}` with required `phases`; phase shape is exactly `{name,tasks}`; task shape is exactly `{name,description,status}`. `status` is required, uses the same enum, and is never optional. Every object rejects unknown keys, including `legacyIdentifier`. Names/descriptions are trimmed non-empty; phase names are globally unique and task names unique within each phase. Phase maps to task group and task maps to todo, preserving order. Legacy is restore-only and maps no identifier.

## 8. Consumer and Exclusion Boundary

Under the accepted contract, formatter, widget, tool frame, reminder, and compaction read only the coordinator snapshot, render required fields and empty/error states, and do not maintain a second model or mutate state. Those consumers must have no dedicated `workingOn` projection. Excluded remain IDs, rename/edit/delete, current-call legacy compatibility, package persistence infrastructure, filters, pagination, and provider variants.

### Compact Widget Status Counts

In the persistent Todo widget's first summary row only, display the complete decimal task count (including empty groups) as `<N> task` for one task or `<N> tasks` otherwise, after `Todos` and before the four status counts. Each status count must be displayed as `<glyph> <decimal count>` instead of a status-name/count label, with one ordinary space (U+0020) between each glyph and count in both glyph modes. Retain the existing ` · ` separators, the fixed order `in_progress`, `pending`, `completed`, `cancelled`, and all four counts including zeros. For this count row, `in_progress` uses the static Nerd Font `nf-md-progress_clock` glyph `󰦖` (U+F0996), or `◔` (U+25D4) with `fallbackGlyphs`. The remaining counts keep the existing `todoGlyph(status, fallbackGlyphs)` mapping: by default `pending` uses `󰄰` (U+F0130), `completed` uses `󰄴` (U+F0134), and `cancelled` uses `󰍷` (U+F0377); fallback glyphs are `○` (U+25CB), `✓` (U+2713), and `×` (U+00D7), respectively. No new font-detection behavior or configuration is introduced. For example, two tasks with counts of 1, 2, 0, 0 render as `Todos  2 tasks · 󰦖 1 · 󰄰 2 · 󰄴 0 · 󰍷 0` before existing theme and width fitting.

While visible, the widget emits exactly one row per canonical task in original order after the summary, without filtering terminal or empty groups, a task cap, a global anchor, or `+N`. Each nonempty task shows its existing status glyph and `task 󰄾 todo` text (Nerd Font `nf-md-chevron_double_right`, U+F013E), or `task › todo` (U+203A) with `fallbackGlyphs`, for the first `in_progress` todo in that task, otherwise its first todo regardless of status (even if terminal and followed by pending work). The separator belongs to layout only; slash characters within task or todo names remain unchanged. An empty task shows its task name alone, without a fabricated todo, separator suffix, or status. Descriptions and other todos do not appear in these rows. Counts cover the complete snapshot, not only representatives. With undefined state the pure layout emits a zero-task summary; in general it emits `1 + tasks.length` nonblank width-fitted rows, with the existing optional component spacer below an above-editor widget. `maxVisible` and `maxVisibleTasks` do not omit task rows. Narrow widths may truncate text horizontally, never omit rows vertically. The projection is read-only and presentation-only: it changes no canonical selection, store, sort order, protocol field, persistence, or business logic. Existing widget visibility and five-second terminal hide, placement, tool rendering, reminders, compaction, and navigation remain unchanged. A finite Host viewport may clip emitted rows; Section 9 governs interactive expansion and bounded access to full details. Verification covers both glyph modes, full task/status counts including zeros, per-task selection, empty and terminal-first fallback, unbounded collapsed row count, and width-bounded rendering.

## 9. Accepted Above-Editor Inline Interaction

This section supersedes Section 8 **only** for inline presentation and detail entry. When no task is expanded outside interaction, the Section 8 summary, task-row projection, order, counts, optional spacer, and `1 + tasks.length` nonblank row contract remain. Active selection uses expandable headers even before a task is expanded. Expanded content stays visible after interaction ends, within the same bounded viewport; the fixed row-count requirement does not apply until those tasks are collapsed or the widget is cleared. The former Section 8 overlay-retention requirement and the earlier Compact Work/Plan's overlay-opener and no-`onTerminalInput` requirements are superseded for this interaction alone. Other Compact and protocol contracts, including qualified-command discovery and shortcut collision rules, remain. The earlier overlay implementation and live-verification gap are historical, not evidence of inline acceptance.

`/todo-details` and the already registered `Key.ctrlShift("t")` shortcut must enter interaction on the **existing visible above-editor Todo widget**. Both use one entry path against the current coordinator snapshot; neither opens a custom overlay, creates another detail command, or changes settings/placement to force a widget. In non-TUI mode, or if the widget is off, below-editor, absent, terminal-cleared, or otherwise unavailable, notify the user without consuming editor input or opening an alternative view. Pi's resolved Todo command remains the fallback when the shortcut loses a native collision; duplicate command names are discoverable by native qualified-name/source attribution, not a presumed suffix.

The widget must keep a local selected task and an independent expanded/collapsed state for each task. The selected task header uses the existing theme `selectedBg` background while retaining status-dependent foreground colors; no `>` marker or reserved selection column is rendered in any row. Chevron-to-status/title spacing remains one space. Initially select the first task with an `in_progress` todo, otherwise the first with a pending todo, otherwise the first nonempty task, otherwise the first task; zero tasks have no selection. A fresh session starts with all tasks collapsed, preserving the Section 8 rows until explicitly expanded. Reentry into the same session retains expansion. `Up`/`Down` move and reveal the selected task header, `Left` collapses it, `Right` expands it, and `Enter`/`Space` toggles it; boundary keys are no-ops without changing the editor. Expanded task headers keep the down expand indicator but show only the task name: no task-leading status glyph, representative todo or layout separator. Each child todo row is indented four spaces beneath its task, retains its own status glyph, and wraps its name and description aligned after the six-column child prefix where width permits; at very narrow widths indentation yields to complete text and the status glyph. Slashes in user-authored text remain untouched. Expanded tasks show every todo in canonical order with its status glyph, complete name, and complete wrapped description, including terminal todos. Empty task headers remain selectable. Expanded headers use the existing Nerd Font/fallback glyph setting for down/right expand indicators; no font detection or new configuration is introduced. Expansion, selection, and scroll position are presentation-only, never canonical state or tool data.

The component must own a bounded viewport of rendered content rather than emit an unbounded expanded body for Host clipping. Width must be bounded by the supplied render width; height must account for current terminal geometry and retain a content row at small sizes. The summary and task headers must remain discoverable by task navigation. `PageUp`/`PageDown` must scroll the detail viewport without changing selection; repeated `PageDown` must expose the final wrapped description of an expanded task larger than the viewport. Selection or expansion must reveal its header; resize and content changes must rewrap and clamp offsets. No description may be vertically elided, and no expanded row may be made permanently unreachable by Host clipping. An empty or insufficient terminal must fail without corrupting editor input; verification must demonstrate actual dock visibility, not infer it from the component's returned lines.

While interaction is active, a narrowly scoped public `ctx.ui.onTerminalInput` listener may consume **only** exact recognized Todo navigation/expansion/scroll keys and `Escape`, and must leave all other input, including bracketed paste payloads, editor commands, and unrelated shortcuts, untouched. It must not parse private terminal protocols or claim global ownership of terminal input. A terminal delivering an unbracketed single key-equivalent paste cannot be distinguished by this public listener; live verification must report that limitation rather than claim universal paste isolation. `Escape` ends interaction, removes the listener and selection controls, and restores ordinary editor input without deleting the existing widget or collapsing expanded entries. Expanded entries remain displayed in the bounded viewport and remain expanded on reentry in the current session; reentry restores navigation and scrolling to reach complete descriptions. A complete `todo_set`, session restore/switch, widget hide/off/clear, or teardown discards expansion; a same-session widget refresh retains it only for task names still present, never by row index. No expansion is persisted or written into canonical state. One active listener at most; repeated entry must not stack listeners. Widget refresh/replacement, hide/off, restore, terminal-clear timeout, failure, and session teardown must retire the old component's listener. Stale listeners must never consume keys after disposal. This exception does not relax the previous prohibition on private Host imports, raw terminal subscriptions, protocol changes, or separate canonical state.

Acceptance requires focused tests for input consumption/passthrough (including bracketed paste and shortcut collision), command and shortcut parity, empty/absent/other-placement notices, all-task rendering, independent expansion, width/height bounds, final-description reachability, and teardown on every replacement/clear path. Same-graph live TUI checks must observe editor passthrough after Escape, regular/fullscreen keyboard behavior, dock visibility at narrow and short sizes, and no interception of other active Host surfaces. Public API availability establishes a plausible route, **not** proof that the Host grants a usable above-editor viewport or safely isolates active input. If either fails in live verification, stop and report the infeasibility; do not silently add a Host change, overlay fallback, or another input route.

### Compatibility

A valid add to a previously missing task now succeeds and creates it. A mistyped or differently cased task name must therefore create a distinct task rather than return `not_found`: for example, adding to `BUILD` when only `Build` exists must append a new `BUILD` task and preserve `Build`. No automatic correction, merge, or replacement is permitted. Invalid untrimmed or empty names must still fail rather than create a task. `todo_set` remains complete replacement with new statuses `pending`; `todo_transition` retains its missing-target rejection. Existing schemas and complete-checkpoint eligibility and rejection rules remain unchanged.
