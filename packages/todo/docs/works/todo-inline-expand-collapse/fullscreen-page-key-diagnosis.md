# Fullscreen Todo Page-Key Input Diagnosis

## Boundary and reproduction

Diagnosis of the existing above-editor Todo widget only; no correction was applied. The archived [live acceptance captures](live-acceptance-captures.zip) and [criterion matrix](evidence.md) are preserved. In isolated Windows ConPTY sessions (100x35, then short viewport), the current Todo source was loaded into installed `@earendil-works/pi-coding-agent` / `@earendil-works/pi-tui` **0.85.1**. After `/todo-details`, expand Build with Right and send separate `ESC[6~` PageDown presses. In regular mode the fourth press reaches `FINAL_DESCRIPTION_SENTINEL live last line verification`; in fullscreen 14 presses produce only 16-byte synchronized-output frames, with no changed Todo detail row. A second short-viewport run repeats the fullscreen failure. Down to Empty can expose the last description, but does not satisfy PageDown scrolling. This is archived VT/key evidence, not a pixel screenshot or a physical-key test. The prior live picker check shows that after Ctrl+L, Down moves the Host model picker and the first Escape dismisses it in both modes.

Independently, an in-memory `node --input-type=module -e` check against the installed TUI created a `TuiAltScreen`, stubbed terminal response handling/viewport height (20)/`scrollBy`, added a listener returning `{consume:true}`, then dispatched `ESC[6~` and `ESC[5~` through `handleTerminalInput`. Assertion result: extension listener received `[]`; viewport `scrollBy` received `[16,-16]`; listener count was 2. This isolates registration order and both page directions without altering the Host. It does **not** prove the proposed Host change works, nor by itself establish Todo's rendered offset.

## Verified cause and ownership

- Installed TUI `node_modules/@earendil-works/pi-tui/dist/tui-alt-screen.js:103` installs its viewport input listener in the constructor. `dist/tui.js:549` stores listeners in an insertion-ordered `Set`, and `dist/tui.js:655-677` invokes them before focused-component input, returning immediately on `{consume:true}`. `dist/tui-alt-screen.js:538-548` matches unmodified PageUp/PageDown, scrolls the transcript, and consumes the key; its overlay deferral at lines 452-454/536 applies only to a focused overlay. The Todo widget is not an overlay.
- Installed Host `node_modules/@earendil-works/pi-coding-agent/dist/modes/interactive/interactive-mode.js:1861-1874,1903` registers `ctx.ui.onTerminalInput` with `this.ui.addInputListener`; Todo registers on entry at `packages/todo/src/widget.ts:68-93`, after TUI construction. Therefore its `TodoWidgetComponent.handleKey` PageUp/PageDown branch (`packages/todo/src/widget-component.ts:67,73-74`) is unreachable for default fullscreen page keys. Regular mode has no competing viewport listener. This is upstream dispatch preemption, not a demonstrated arithmetic/clamping defect in Todo.
- Installed public API `node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts:45-53,77-100,116-127` offers a listener without priority/focus options, a presentation widget, and separately `custom()`/overlay. `docs/keybindings.md` explicitly assigns unmodified fullscreen page keys to transcript and Ctrl variants to editor by default, with user-configurable bindings. `docs/extensions.md` and `docs/tui.md` describe widgets as persistent presentation and custom/overlay as separate focused UI. A Todo-local keybinding remap would change transcript/editor semantics globally; a private listener reorder would rely on internal Host state; switching to a focused custom overlay would change the inline dock/editor/focus contract. None is a supported Todo-local fix for this same widget and its required PageUp/PageDown behavior. A custom overlay could be a separate product design, not a demonstrated minimal correction.

## Smallest proposed correction (not implemented)

Owner: matching-version **Host TUI** input dispatch, not Todo offset handling. Make the fullscreen viewport input handler run as a *fallback* after public input listeners have had a chance to consume/transform input, but before forwarding remaining input to the focused component. In `@earendil-works/pi-tui` source corresponding to installed `dist/tui.js:655-720` and `dist/tui-alt-screen.js:103,461-548`, stop registering `handleViewportInput` as the first ordinary listener; expose a protected unconsumed-input hook in `TuiBase.handleTerminalInput` and implement it in `TuiAltScreen` by returning whether `handleViewportInput(data)` consumed. Keep terminal protocol responses guarded ahead of extension input and keep search/overlay and mouse behavior under review when moving the handler. No public extension API or Todo source change is needed for this candidate. The precise placement and compatibility impact must be reviewed in the matching Host source before implementation; blanket listener reordering or disabling transcript bindings is not a verified fix. Host `InteractiveMode.addExtensionTerminalInputListener` need not change if public listeners are processed before the fallback. Ordinary fullscreen page keys should continue to scroll transcript whenever no extension consumes them; Ctrl-page variants and existing user keybinding overrides retain their established routing.

Regression procedure in matching Host repository: add a `TuiAltScreen` input-order test beside its keyboard viewport tests, using a virtual terminal, enough transcript rows to scroll, and a consuming extension-like input listener registered **after** constructing the TUI. Send separate press/release PageDown and PageUp sequences; while listener is active, assert it receives both presses and that viewport position is unchanged. Unsubscribe, resend each key, and assert normal transcript scrolling in both directions. Include a passthrough key that reaches the focused component and verify focused-overlay viewport deferral still works. In a Host integration test or the ConPTY rerun, open a native selector while Todo is active and assert that, after Todo retires its listener on the opening chord, Down and the first Escape belong to the selector. Then rerun the archived fullscreen ConPTY scenario with the matching Host build: after expanding Build, repeated PageDown must reveal the final description in the dock; PageUp must reverse detail offset; Escape retains expansion; Ctrl+L picker Down and first Escape still work; after Todo exits, page keys scroll transcript and editor input remains usable. Existing regular-mode behavior must remain intact. The in-memory check above is the pre-fix failing expectation; no post-fix run is claimed.
