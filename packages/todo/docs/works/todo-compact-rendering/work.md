## User Outcome

Keep the persistent Todo widget useful by showing the full task count and one representative row for every task while it is visible under the existing lifecycle. The existing below-widget spacer may remain. A Todo-owned detail overlay exposes the complete snapshot when requested and supports keyboard navigation plus mouse expansion/collapse in fullscreen Pi. This later user-authorized all-task display supersedes the fixed-height/global-anchor acceptance criteria below only for the persistent widget; the original Gate C record remains historical evidence, not acceptance of the new display.

The detail surface is a focused Pi custom overlay, not a sidebar. It opens from a dedicated command and shortcut, uses Pi's public overlay and TUI interaction surfaces, closes with Escape, and returns focus to the prior component.

## Scope

- Replace the persistent widget's task-by-task projection with a width-bounded summary whose row count is independent of snapshot size.
- Preserve the current widget placement, visibility, restore, refresh, five-second terminal-state display, and fault boundary.
- Add the `/todo-details` command and `Key.ctrlShift("t")` (`Ctrl+Shift+T`) shortcut, which open the same overlay against a cloned current coordinator snapshot. The resolved Todo command remains the public fallback when Pi skips or supersedes a colliding extension shortcut; duplicates use Pi-qualified invocations discovered through native autocomplete (Plan §5).
- Show canonical task order and complete todo data in the overlay. Task headers expand or collapse; expanded tasks show todo status, name, and description.
- Support complete keyboard interaction in regular TUI mode and keyboard plus public Pi mouse regions/handlers in fullscreen/alternate-screen mode.
- Coordinate the root and Todo manifests plus repository lockfile on the exact public mouse baseline `0.85.1`: root `package.json`, `packages/todo/package.json`, and root `bun.lock` jointly own the three-package graph.
- Keep overlay interaction state local to one open overlay and discard it on close.

## Acceptance Criteria

1. While visible, the widget emits `1 + tasks.length` nonblank width-fitted rows: a summary and one row for each canonical task in original order, including empty and terminal groups. The optional above-editor spacer remains. The finite Host viewport may clip rows; complete detail remains available in the overlay.
2. The summary reports the full task count and all four fixed-order status counts including zeros. Each nonempty task row shows its first `in_progress` todo, otherwise its first todo regardless of status, with the existing status glyph and `task / todo` form. Empty tasks show their name alone. Selection is independent per task; there is no global anchor, `+N`, or task cap. This read-only projection does not select or modify canonical state, protocol, persistence, or other consumers.
3. Existing placement, off behavior, event refreshes, restore behavior, terminal five-second display, clear timing, and warning behavior remain unchanged.
4. `/todo-details` and `Key.ctrlShift("t")` (`Ctrl+Shift+T`) share one opener. Outside TUI mode they do not attempt an overlay and report the unsupported mode through the existing UI notification surface. Pi's native shortcut diagnostics and winner rules remain authoritative: a reserved collision skips this shortcut, and a later extension collision may supersede it; neither removes the resolved Todo command. `/todo-details` is unqualified only when unique; duplicate registration suffixes every command. Discover the actual qualified Todo invocation through native autocomplete description/source attribution and verify its source through public `pi.getCommands()`. Ambiguous attribution visibly fails admission; never assume a suffix.
5. In regular and fullscreen TUI modes, the opener uses `ctx.ui.custom(..., { overlay: true })`. The overlay renders all canonical task headers, expands only local presentation state, and never mutates or publishes Todo state. Regular mode retains complete keyboard operation and does not accept Pi-captured mouse input.
6. Initial detail selection is deterministic: first task containing an `in_progress` todo, otherwise first task containing a pending todo, otherwise first nonempty task, otherwise the first task. Initially expanded groups are those containing `in_progress` todos; if none exist, only the selected usable group is expanded.
7. Up/Down move task selection and reveal the selected header; Left collapses; Right expands; Enter/Space toggles; Home/End select and reveal the first/last task; PageUp/PageDown scroll the detail viewport without changing selection. Free scrolling may move the selected header off-screen until a selection or expansion command reveals it again. Escape closes. Expanded descriptions wrap in full and remain discoverable; repeated PageDown reaches the final todo of a task taller than the viewport entirely by keyboard.
8. In fullscreen/alternate-screen mode, a primary click on a task header selects that task and performs exactly one expansion toggle, including when it was previously unselected. Expand/collapse leaves the clicked header visible and makes it the keyboard cursor; the next keyboard operation acts on that task. Public `MouseRegion`/`Component.handleMouse` contracts handle that activation exactly once. Non-header and non-primary clicks return unhandled. Separately, the overlay's public `handleMouse` consumes signed `wheelDelta` events inside its bounds, clamps its own offset, and returns handled even at boundaries; no ScrollView/main-layout wheel fallback is assumed. Regular mode accepts no Pi-captured mouse input. No mode uses `onTerminalInput`, direct terminal parsing, private imports, or non-barrel dispatch internals.
9. Closing by Escape or command completion disposes overlay-local state and restores the previously focused Pi component. Reopening reads a fresh cloned coordinator snapshot.
10. Narrow terminals do not overflow, create negative dimensions, or resize based on labels. Long task and todo names truncate or wrap within overlay bounds; descriptions wrap in full within those bounds and remain keyboard-discoverable; selection and expansion do not change outer overlay dimensions.
11. Empty state is a bounded overlay state and is closable by Escape. Large snapshots remain navigable through overlay-owned bounded offset/clamping/render slicing with public keyboard and wheel input. Rewrap and clamp on resize; preserve a content row at minimum height. Selection and expansion commands maintain selected-header visibility; PageUp/PageDown intentionally permit free scrolling away from that header.
12. Focused tests, affected-workspace tests/typechecks, lock and manifest checks, diff checks, and real interactive Pi verification against one installed exact coordinated `0.85.1` graph establish summary bounds, exact entry registration, regular-mode keyboard-only behavior, oversized-body PageDown reachability, fullscreen keyboard and mouse behavior, click-then-keyboard continuity, explicit overlay wheel handling, deliberate duplicate-command qualification/discovery (including unavailable shortcut and ambiguous-discovery visible failure), focus restoration, and path containment.
13. Compact writes to `packages/todo/src/tool.ts` and `packages/todo/test/index.test.ts` wait until Todo Review Fixes Slice B completes B2 and then Slice A completes A2 and both release their paths. The bytes are re-read before compact work begins and before integration. `packages/todo/README.md` remains exclusively Slice C-owned through C2 and is never modified by this Work.
