# ADR-0002: Use Structured Resolver Input and YAML Handoff/Result Messages

- Status: accepted historical baseline; Model Role selection and schema availability superseded by ADR-0009; structured Handoff and YAML Result decisions remain current; direction A amended to one join and file-reference/generic reading, accepted but not implemented
- Date: 2026-08-17
- Decision identity: ADR-0002 continues to own structured Resolver input and YAML Handoff/Result messages; the amendment below refines rendering and Result delivery within that same decision, not a new protocol lifecycle.
- Amendment delivery status: current product choice reconciled in this ADR and the three owning Specs; target-contract synchronization and independent substantive audit are complete, with non-normative stage wording corrected here. The affected unconfirmed and unexecuted initial Plan/Waves graph still requires rederivation and current implementation-scope confirmation; implementation, actual Host/Router acceptance, and live provider acceptance remain outstanding. This records the same accepted decision, not implementation confirmation.

## Context

The Model Role wording below records the historical baseline. Its selection and schema-availability requirements are superseded as defined in [#42 Partial Supersession](#42-partial-supersession).

Free-text task forwarding copies unnecessary context, weakens validation, and lets workflow instructions drift. The Router also needs Pi to constrain its choice to Skills and Model Roles currently available in the session.

## Decision

The Router calls `resolve_delegation` with a structured Handoff object. The extension generates the tool schema at runtime from discovered Skills and configured Model Roles, so `primarySkill`, `companionSkills`, and `modelRole` are dynamic enums before model generation begins.

The Handoff delivered to a Handler is YAML. It contains `objective`, `primarySkill`, `companionSkills`, `context`, optional `constraints: string[]`, and optional `deliverables: string[]`. Model Role is runtime routing metadata and is not part of the Handoff prompt. `companionSkills` is unique and cannot repeat `primarySkill`.

Each context item is either:

- `{ ref, purpose }` for a readable absolute path or a workspace-relative path; or
- `{ inline, purpose }` for short, unpersisted session decisions.

The Resolver checks and canonicalizes every `ref` without inlining it. URLs and inferred context kinds are out of scope.

Handlers return YAML Results with `status`, `summary`, and Markdown `report`; `artifacts` may reference produced files. `completed`, `partial`, `blocked`, and `failed` distinguish complete work, useful incomplete work, missing external conditions, and attempted technical failure. Results must not contain a workflow-controlling next action or Skill recommendation.

## Consequences

Schema validation happens before delegation and references avoid automatic context inlining; this does not establish token, cache-hit, or cost savings. The Router receives stable, normalized Result information but remains solely responsible for deciding what happens next. Dynamic schemas must be refreshed when Skills change. The historical requirement to refresh Model Role enums on Role configuration changes is superseded below.

## Accepted Amendment: Stable YAML and Protected Result Reading

This historical heading and anchor retain the same amendment identity. “Protected Result reading” no longer promises a dedicated protected reader; the current decision is initially trusted file-reference delivery followed by Router-owned generic reading.

### Context and decision drivers

The accepted [product amendment](../prd/router-delegation.md#stable-delegation-and-protected-result-reading) calls for predictable messages and manageable long Result delivery without losing evidence or mixing executions. Direction A, the inclusive 16384-byte decoded-original UTF-8 threshold, unchanged existing-summary reuse, and complete first-adoption evidence remain accepted. The latest user confirmation, “join 不要第二个，返回 ref 后，router 自行 read”, replaces the earlier protected-reader refinement: one ordinary join returns a long-Result summary plus the existing `resultPath`, and the Router uses ordinary `read` on the existing JSON envelope and fully decodes its `result`. The user explicitly accepted reduced subsequent read-time protection and native-read capability limits, without changing storage or adding a body copy. This is a local revision of the same accepted architecture with Spec target-contract synchronization and independent substantive audit complete, but implementation outstanding, not a new ADR lifecycle or a claim about current tools.

The supplied file-reference assessment at `c:/Users/WINDOWS/.pi/agent/sessions/--E--Projects-pi-packages--/2026-08-16T11-58-37-784Z_01a00a70-28d7-789b-8c64-0d784f30d9b4/tasks/assess-result-ref-generic-read-artifacts/result-1.json`, generation 1, records that the existing `resultPath` identifies a compact single-line JSON transport envelope with escaped Result newlines, not decoded YAML. It reports native-read failures for oversized single physical lines and that ordinary reads do not inherit Herdr’s per-read protection. The assessment’s candidate storage change and unresolved choices are not current alternatives: the subsequent user confirmation retains the existing representation and accepts the ordinary-file boundary. Its source and synthetic in-memory checks are prior evidence, not checks rerun by this amendment or actual Host/Router acceptance. A terminal join snapshot alone does not freshly establish trusted disk content; fresh source validation before reference issuance remains required.

The drivers are unchanged message meaning, minimal additional mechanisms, truthful incomplete delivery, complete evidence before adoption, execution isolation, and Router-only judgment. Stable rendering and the reduced subsequent read boundary must not weaken authorization, admission/current-byte validation, exact invocation forwarding, first safe publication, or initial source trust.

### Accepted decision

1. **Retain YAML and make rendering deterministic.** Equivalent validated inputs under the same instructions produce the same YAML rendering. Preserve meaningful array order and user-supplied content; do not sort arrays to manufacture common prefixes. Keep stable instruction content stable and changing request-specific content in the dynamic tail. This refines rendering, not the closed Handoff/Result schemas, model selection, or existing admission identities. The exact rendering rules are now defined in the synchronized Router Spec, not newly selected here.
2. **One join: short full delivery; long summary plus existing file reference.** Measure decoded-original UTF-8 bytes, excluding envelope escaping and metadata. At most 16384 bytes returns the full original; above that boundary, reuse `HandlerResult.summary` without rewriting it and return the exact existing task/generation `resultPath`. Before issuing the reference, the backend freshly establishes trusted source content and current scope/task/generation association; cached terminal content alone is insufficient. Retain necessary association evidence and explicitly state that full content was not returned. Navigation is neither an adopted Handler Result nor a business-success judgment. There is no second join mode, inspect full-reading branch, or dedicated full-reading interface; an issued path does not prove complete native readability.
3. **Router reads and decodes the existing envelope with generic `read`.** The Router obtains the complete existing JSON envelope through ordinary file reading, decodes JSON to recover the exact `result` string, and actually reads the Handler Result; escaped JSON is not decoded YAML. The existing file is neither a separate original-body copy nor a protected capability. Storage representation remains unchanged. Subsequent ordinary reads rely on Host/OS permissions and Router correlation, not Herdr per-read task/identity, private owner/ACL, or original-continuity checks. A path is not a revocable token: it promises neither automatic lifecycle invalidation or real-time revocation, a same-file snapshot across reads, nor detection of equal-length original replacement. Current scope/task/generation and complete evidence must still be correlated by the Router; visible conflicts or uncertain association prevent adoption. This is not an equivalent replacement for the former protected-reader guarantees.
4. **First adoption still requires complete reading and judgment.** The Router must obtain and actually read the complete same-source Result, correlate scope/task/generation to the selected outcome, distinguish Handler `completed`, `partial`, `blocked`, and `failed`, and evaluate required evidence, limitations, and applicable item/Wave predicates. A navigation summary, excerpts, backend validation, terminal notification, or transport success cannot substitute. Backend terminal status and Handler status remain separate. Once complete reading and correlation remain established, later work may use necessary excerpts and original references without repeated full return; excerpts must retain source association and material limitations. Lost or uncertain adoption evidence cannot be replaced by assuming the original was read earlier. No automatic history deletion or consumption-confirmation mechanism is selected.
5. **Fail closed on incomplete or uncertain reading and correlation.** Missing/unreadable content, unavailable permissions or generic reader, stale or mismatched scope/task/generation, malformed content, visible source conflicts or uncertain association, native-limit failures, and truncation/unknown completeness leave the affected predicate unsatisfied. Preserve the first established semantic state, report the concrete gap, and do not adopt, infer completion or absent effects, invent a Handler status, or release affected dependencies. Do not silently retarget an old reference to another task or latest generation. The compact single-line envelope can exceed native read capabilities; line offset/continuation cannot recover an oversized single physical line. If ordinary `read` cannot obtain complete content, report the limitation without a dedicated-reader or bypass fallback, storage change, or summary-only adoption. Native limits are environmental capabilities, not an application output budget or page size. No all-length recovery is guaranteed. Reading authorizes no launch, resume, cancel, remove, file repair, or cleanup.
6. **Keep ownership, initial protection, and isolation intact.** The Resolver retains admission/current-byte and current-call/JIT validation, exact fixed-`handler` and resolved `prompt`/`model`/`thinking` bindings, and raw launch evidence without business interpretation. Delivery projection and fresh trusted source validation before reference issuance belong to the backend adaptation contract, not a new Resolver projection or correlation layer. First safe publication and initial generation/source validation remain required; ordinary-file reading changes only the subsequent read boundary. The Router alone owns authorization, semantic backend eligibility, first adoption, evidence judgment, status projection, and dependency release. Scope/task isolation and image/non-text handling remain intact: a file reference grants no other-task or image access, and no cross-task shared session or Result reuse is introduced. The [Router Spec](../spec/router-delegation.md#launch-evidence-and-router-progression) and [Backend Adaptation Spec](../spec/backend-adaptation.md#2-compatibility-requirements) retain those safety owners; their target contracts are now synchronized and independently substantively audited; the earlier dedicated-reader guarantees do not continue under this amendment.

Observation/privacy has a distinct ADR lifecycle. [ADR-0011](0011-in-process-observation-privacy.md#withdrawal-and-current-authority) records the user's withdrawal of observation; it creates no current implementation, collection, or control-entry obligation for this amendment.

### Considered alternatives and rationale

- **A — retain YAML and the original Result, refine rendering and later consumption (accepted, revised).** Complete first consumption and later necessary excerpts/original references remain. The current refinement reuses the existing summary and file path in one join, then uses generic reading and JSON decoding without a new protocol, storage representation, or body copy. It preserves evidence ownership while deliberately reducing subsequent read-time guarantees.
- **Earlier protected-reader refinement (historical, replaced).** Dedicated full access, inspect reading selection, a second join/full-return mode, and token-based protection are not the current decision. The latest confirmation chooses the ordinary-file boundary, not a new tool, token/registry, pagination, or reconstruction of the discarded guarantees.
- **B — add a layered material-access system (not selected).** The comparison considered separate summary navigation, full Result, and attachment access as a larger material-access approach. Its additional reading contracts, view consistency, and storage-maintenance obligations were not justified for this bounded change. A's refined delivery does not adopt B's larger system. No unaccepted B schema or persistence mechanism is recorded as a contract; observation history belongs to its separate, withdrawn lifecycle.
- **Keep full default delivery and offer only an explicit summary mode (compatibility alternative, not the accepted default).** This preserves more existing caller assumptions but does not implement the accepted long-Result default. No mode parameter is selected. Summary-only adoption remains unacceptable because it omits complete evidence; ordinary-path reading is now accepted only with initially trusted issuance, complete decoding/reading, and Router correlation, not as a claim of equivalent protected access.

### Consequences and compatibility

Predictable rendering and original-based navigation retain YAML and avoid a new message/storage framework. Reusing `HandlerResult.summary`, the existing `resultPath`, and generic `read` avoids a new summarizer, dedicated reader, token/registry, or body copy. The tradeoff is explicit: subsequent reads no longer receive Herdr per-read identity, private owner/ACL, or exact original-continuity validation. Host/OS permissions and Router association remain, but paths are not revocable capabilities and cannot guarantee same-snapshot reads or equal-length replacement detection. Removing those subsequent guarantees does not remove first safe publication or fresh trusted source validation before issuing a reference.

A second negative consequence is availability: native `read` can fail to supply the entire compact single-line JSON envelope. Issuing a reference, retaining the original file, or short-Result full delivery does not prove arbitrary-length readability. No array storage, rewritten envelope, application output budget/page size, new body copy, dedicated full-content entry, or bypass read is selected to hide this gap. Failed or uncertain complete reading leaves first adoption and dependency release blocked. Actual Host output and Router full evidence consumption remain unverified.

Changing long Results from full default return to navigation is a real compatibility impact: one successful join no longer implies receipt of the full Result. Short full delivery and retention of the same file do not make this fully compatible. Callers, tool descriptions, tests, progress returns, and all model-visible projections must distinguish navigation from full content and direct the Router to generic envelope reading/decoding before first adoption. A summary must not replace a field still represented as the complete opaque original; hidden long-body delivery in another projection is not evidence of reduced model input. Compatibility also includes the deliberate reduction in subsequent protection, not merely a renamed reference. Backend-specific target mapping is now defined in the synchronized Specs; caller adaptation remains an implementation obligation, without changing the Resolver’s raw-return responsibility or join’s existing waiting, settlement, and cleanup lifecycle.

There is no promise of fewer first-adoption total tokens, cache hits, cost, TPS, or disk I/O. First adoption still reads the whole Result; navigation, metadata, and extra calls can add input. Stable rendering and process-local content reuse do not demonstrate provider-cache behavior. Technical authority acceptance is not implementation confirmation, runtime activation, or live Router acceptance.

### Revisit conditions

Revisit the affected decision if evidenced native-read limitations make the accepted availability tradeoff inadequate, caller migration cannot distinguish navigation from full content, initial source trust or Router association cannot be retained, or execution/non-text isolation would be weakened. A renewed need for real-time revocation, same-snapshot reads, or equal-length replacement detection requires explicit acceptance and owning authority reconciliation; it must not silently restore dedicated tools/tokens, a second join, pagination, or storage changes. Measured workload evidence that A is insufficient may justify reconsidering B or the default-delivery choice; cache or token assumptions alone do not. Renewed observation requires explicit acceptance under its separate authority, and changed first-adoption evidence requirements need their own authority rather than reinterpretation of a summary.

## #42 Partial Supersession

Accepted [ADR-0009](0009-provider-model-thinking-capability-selection.md) supersedes the Model Role selection and schema-availability portion of this ADR. The historical requirements for configured Model Roles, a dynamic `modelRole` enum, and Role-configuration-driven schema refresh are no longer current implementation obligations. Legacy `roles`/`modelRole` fields are rejected under ADR-0009 rather than retained as a compatibility interface.

The current Resolver root carries non-negative integer `reasoning` and `impact` requests, and the Resolver selects a configured provider/model/thinking candidate under ADR-0009. Schema generation does not read the Registry, filter candidates by availability, or attest their availability; candidate availability and thinking support use the single resolve-time Registry snapshot defined there.

The structured Resolver input, dynamic Skill enums, YAML Handoff shape and reference handling, primary/companion Skill uniqueness, and four-state YAML Result contract remain current. The Handoff continues to exclude model routing metadata and now also excludes capability requirements. Router ownership of workflow decisions and the prohibition on workflow-controlling Result fields remain current. This partial supersession preserves the original date and historical rationale; it does not establish live Pi or backend verification.
