## Context

The main session must select useful work without accidentally doing delegated work itself. The Resolver must validate and invoke the selected delegate without owning a subagent runtime, interpreting Handler Result business content, or advancing work.

## Decision

The package separates four responsibilities:

- **Router**: responds directly when appropriate; otherwise selects Skills, semantic non-negative integer `reasoning`/`impact` requirements, context, constraints, and deliverables, establishes delegate compatibility, and supplies its registered tool name and startup parameters to `resolve_delegation`. The 0..3 values are examples of request vocabulary, not phase levels. The fixed Agent is the literal `handler`, never a path or Agent body. The Router alone interprets raw launch status/evidence, correlates the full Handler Result, projects main-session Todos and Waves, checks evidence and predicates, releases satisfied dependencies, and makes subsequent workflow decisions. Partial, blocked, failed, and uncertain evidence cannot become completion by inference.
- **Resolver**: validates a structured Handoff, validates Skills and local references, resolves one available candidate from nested `harness.candidates` using exact provider/model/thinking fields, deterministic capability-surplus ordering, and one resolve-time Registry snapshot, serializes the Handoff to YAML, and returns exact model/thinking metadata. It also validates the Router-supplied registered delegate-tool name and startup parameter object, binds protected generated values exactly, rejects collisions, and invokes that existing tool through the host execution API. It returns resolution plus the raw nested launch return or error evidence under the [Backend Adaptation Spec](../spec/backend-adaptation.md). It does not normalize backend status into a Handler outcome, interpret Handler Result business content, correlate or project Results, release dependencies, choose an alternate tool, apply an independent tool-category allowlist, retry, or manage lifecycle.
- **Environment / delegate backend**: registers the delegate tools and owns their execution semantics. The selected tool receives the fixed `handler` Agent, exact resolved prompt/model/thinking, and Router-supplied startup parameters; compatibility requires stable identity and access to the full Handler YAML Result. Backend return or error evidence does not by itself prove active execution, terminal work completion, or absence of effects.
- **Handler**: performs one delegated outcome and returns exactly one normalized Result. It does not choose continuation or manage Router coordination state.
The historical visible-outcome workflow clarification ([Spec](../spec/router-delegation.md#11-generic-single-result-delegation-contract), [ADR-0005](0005-let-router-adapt-delegate-tools-directly.md#accepted-router-workflow-clarification)) allowed simultaneous Resolver execution calls only on positively proven Host/tool-call parallel capability. The later accepted [evidence-branch scheduling amendment](../spec/router-delegation.md#13-evidence-branch-scheduling-and-strategy-loading) supersedes that simultaneity gate: exact per-outcome Resolver execution calls remain ordered, while independent nonconflicting Handlers may overlap in the background only if the effective delegate tool contract and resources permit successive calls. Shared read-only sources alone do not conflict. Dependencies and conflicting writes (including outcomes writing the same file), ownership, authority, behavioral-contract, and side-effect conflicts serialize. Unknown capability requires a contract-compliant serial path or block; no live backend change is claimed.

Router Todo is bounded to a one-way main-session display. Its sources are explicitly selected Work entries, accepted PRD/ADR/Spec authority, selected Plan/Waves scope, reliable execution facts, and current explicitly identified coordination outcomes. Work is a delivery entry, not sole authority; neither a Todo item nor its status establishes execution permission or business completion. For selected multi-step work, the Router exposes one item per independently observable outcome and truthfully communicates current coordination and terminal Result facts using native fields/descriptions or ordinary coordination messages. Complete Result reading and correlation, actual authorization and scope confirmation, prerequisite predicates, and Wave gate evidence independently govern adoption and progression; successful Todo mutation is not a precondition for them.

The Router may rebuild, replace, or clear the whole display without proving closure of old Results, roles, dependencies, or record identities. Old cancelled/unstarted items, missing Results, same-name records, status regression, and current/active/unresolved duties do not block display changes. Removing an active display item neither cancels its execution nor discharges its actual coordination duties; those duties remain visible through ordinary messages when needed, but accounting for them is not a clear-before prerequisite. A whole-view replacement need not preserve old survivor fields, order, or statuses. Local removal preserves non-target records under the actual callable tool contract. Replacement followed by status transitions is normal source-based derivation, not a cleanup bypass, and does not require a cross-call transaction, IDs, CAS, or new tool.

The Router must distinguish re-deriving established facts from re-adopting a Result or re-releasing dependencies. Duplicate and conflicting Results retain their independent idempotent/fail-closed correlation rules; a new Todo is not an old execution identity continued, and old notifications must not update or delete a new item merely by name. Native `partial`, `failed`, and `blocked` are not required: their Handler semantics remain explicit in descriptions or ordinary messages, never recast as completed. Withdrawal before launch and unconfirmed cancellation of actual active execution must remain distinct. Tool rejection, partial projection, or unknown effects require truthful visible reporting without blind retry, old-snapshot restoration, or fabricated success/absence of effects. Todo changes never alter the execution graph, Results, sessions, manifests, or artifacts and never call `subagent_remove`.

The package replaces Pi's default system prompt, making the main session a Router whenever the extension is enabled. The Router retains Pi tool access for coordination materials but is prohibited by its system prompt from doing project-domain work.

The environment assigns each launched Handler a `taskId`. Terminal delivery must permit correlation of the `taskId` and objective with the normalized Result; a notification may be summary-only when the backend supplies a supported path to retrieve the full Result. The Router reads that full Result and makes a fresh decision: it may start follow-up work, respond to the user, or remain idle for later notifications. There is no batch join rule or wait control tool. This clarification does not change Herdr's notification or join lifecycle.

## Consequences

The package can remain backend-neutral. Prompt discipline, not permission removal, enforces Router restraint in v0.1. Backends must be designed and tested independently, and no backend-specific behavior may leak into the Resolver contract. Main-session Todo state is coordination metadata only and does not replace atomic Handler Results, Resolver legality checks, or durable records that an environment already provides; it is not a new persistent task database or restart/outbox protocol.

The derived-view decision removes the reverse dependency that made a display reconstruction wait for old ledger closure or identity/status continuity. The previous cleanup guarantee treated current/unresolved records and survivor preservation as a whole-view admission boundary; that guarantee is superseded, while actual execution safety and local non-target preservation remain. The positive consequence is that the Router can render the selected current scope without resolving obsolete display history. The tradeoff is that the display is neither complete execution history nor proof of cancellation or completion, and multi-call derivation can leave a partially aligned view; necessary facts must remain honestly visible through existing messages. The [PRD](../prd/router-delegation.md#success-criteria) owns that product outcome, and the [Spec acceptance scenarios](../spec/router-delegation.md#todo-cleanup-acceptance-scenarios) own the actual API, failure, correlation, and later model checks. No synchronizer, scheduler/queue, ledger/receipt, persistent marker, ID/CAS, capability registry, Resolver cleanup path, or new authority layer is introduced. Revisit this display decision if selected sources cannot establish truthful facts or existing message/tool surfaces cannot expose material uncertainty; such a gap does not promote Todo into authority or authorize evidence destruction.

Concurrent independence is a Router judgment constrained by the effective delegate tool contract and resources, not a backend guarantee. v0.1 does not provide worktree isolation, locking, conflict detection, or a task scheduler; shared read-only files alone do not prevent eligible background overlap, while conflicting shared-file writes and other conflicting work remain serialized. The on-demand `delegation-strategy` Skill is Router-only coordination guidance, with implementation pending; it does not expand the Resolver or Handler's authority.

## Work/Plan/Waves amendment for new planned work

The Router owns the selected Work/Plan/Waves scope and confirmation, the decomposition into independently observable items, explicit prerequisite and conflict judgments, Todo projection, and Wave gate/release decisions under the [Spec's planned-work contract](../spec/router-delegation.md#new-planned-work-document-and-release-contract). A Plan links one corresponding Waves document for its selected scope; Waves links back to that Plan and Work. Each item has an observable completion predicate and evidence, and each Wave has an explicit release predicate. Only completed item Results with required evidence satisfy a dependent gate by default; `partial`, `failed`, and `blocked` remain truthful terminal Results without automatic release. Every bounded Handler still returns exactly one Result, and the Router decides again afterward. A Wave is a grouping and evidence gate, not an automatic scheduler or a second Result type.

The Resolver's new-plan legality check selects one linked same-directory Work/Plan/Waves tuple, verifies canonical references and current-call document bytes, and never decides confirmation or semantic gate success; the environment retains its own launch, correlation, and tool limits. The Router preserves exact ordered Resolver validation-and-launch calls, serializes conflicts, and overlaps independent ready items only where the effective backend contract permits. No integrated tool, specific transport, receipt, backend change, or parallel tool-call guarantee follows from Waves. Existing completed Tasks artifacts remain historical; an unfinished Tasks plan needs explicit migration and applicable confirmation before more planned implementation. The inspected source candidate now includes Work/Plan/Waves admission and Router prompt/schema support, including pre-resolution link/item/Wave-prerequisite checks and separate post-projection Wave gate verification. Focused source verification and remediation provenance are recorded in the [migration Context](../works/router-wave-task-graph/context.md); independent re-review is pending. Historical Tasks-based evidence above is preserved and is not evidence of live Waves conformance. No source installation, activation, live Router/Resolver/Handler bootstrap, overall migration acceptance, or join-hang resolution is claimed.
