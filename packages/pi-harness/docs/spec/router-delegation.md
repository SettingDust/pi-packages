## 1. Boundary and trust ownership

The Router/coordinator owns workflow confirmation. For new planned implementation it must complete the Plan and its linked executable Waves document for the selected ready scope, disclose the substantive plan and exact authority in an ordinary message, obtain explicit current-user confirmation of that scope, and then invoke delegation. Historical Tasks-based work is governed by the migration rule in section 1.2. Preparatory analysis, Spec reconciliation, and initial planning use standalone admission and the preparation effect boundary below; they do not require an existing Work/Plan/Waves tuple or implementation-plan confirmation. Section 1.2 defines the workflow and narrow existing-authorization exceptions. A Handoff requests work and never proves acceptance. `@settingdust/pi-harness` does not authenticate the user, interpret natural-language confirmation, persist confirmation, issue a token or receipt, or replay-protect confirmation history.

The Harness Extension owns prompt/tool registration, Resolver execution, and the configured delegate-tool call. The Router owns semantic eligibility: it selects a registered delegate-tool name and startup parameters only after confirming compatibility for this environment. The Resolver validates the closed request shape, resolves the Handler invocation, rejects protected-parameter collisions, and invokes only that Router-selected tool through the host execution API. It returns resolution plus raw nested launch return or error evidence under the [Backend Adaptation Spec](backend-adaptation.md); it does not interpret Handler Result business content, correlate or project Results, advance Todo/Waves, release dependencies, choose a tool, apply a tool-category allowlist, retry, or manage lifecycle. The Router alone interprets launch status/evidence and owns those workflow judgments under the launch-evidence contract below.
The Router's coordination Todo is a one-way main-session display, not Handler input, Resolver state, backend lifecycle state, an execution ledger, or permission. It must derive only from explicitly selected Work entries, accepted authority, selected Plan/Waves scope, reliable execution facts, and current explicitly identified coordination outcomes, including standalone temporary outcomes when selected. Work supplies a delivery entry, not sole product authority; selecting display sources does not confirm implementation or alter graph scope. Selection of one or more concrete Work/Plan/Waves sources happens for the actual display operation, not as a prerequisite for accepting this governance revision. Within selected multi-step scope, expose one item per independently observable outcome; grouping must not merge Results.

The Router must truthfully expose the current coordination action before it acts and the semantic terminal Result after complete reading and reliable correlation, using available Todo fields/descriptions or ordinary coordination messages. Native `in_progress` must rest on reliable active execution or a current coordination action, not an old UI label. `completed` requires a safely correlated completed Result and the outcome's required completion evidence; it does not establish a Wave gate. Handler `partial`, `failed`, and `blocked` remain distinct semantic facts, explicit in descriptions or ordinary messages with the closest truthful non-success native state. Never recast them as completed. Missing, conflicting, or uncertain Result evidence cannot manufacture a Handler status or satisfy completion.

The Router must keep actual execution duties, permissions, scope confirmation, prerequisites, and Wave gates independent of the display. Todo mutation success, a completed label, or an empty display must not prove business completion, cancel actual active execution, or release dependencies. An unavailable or failed projection must be honestly reported through existing ordinary coordination messages and must not block otherwise satisfied execution admission or Result adoption. Rebuilding, replacement, or clearing must not require old Result closure, stable old identities, native-state continuity, or completion of current/active/unresolved coordination duties. Those actual duties still apply and must be communicated when needed, but neither retaining active Todo records nor first accounting for those duties is a prerequisite for clearing the display.

Result correlation uses existing task/runtime identity and available visible evidence. Equivalent duplicate notifications must not re-adopt a Result or repeat dependency release; malformed, conflicting, or uncertain evidence fails closed for the affected semantic outcome and dependents, preserving the first established facts and reporting the gap. Re-deriving already reliably associated facts is a separate display operation and is allowed. A new Todo is not the continuation of an old execution identity: an old notification must not update or remove a new item merely by matching its name. After restart/resume/replay, uncertain Result association prevents re-adoption or release, not rebuilding from other established selected facts. No persistent identity/generation or digest storage, restart/outbox API, exact description mutation, or extra authority layer is required.

The Router may keep independent, nonconflicting delegated outcomes active at once only when the effective delegate tool contract and available resources permit background overlap. Its resolve-to-launch tool calls remain ordered: complete each exact pair before considering the next branch. Shared read-only inputs alone do not conflict. Dependencies and conflicting writes (including independent outcomes writing the same file), ownership, authority, behavioral-contract, and side-effect conflicts require serialization even when overlap is available. Unknown, stale, incompatible, or ambiguous overlap capability requires a contract-compliant serial path or a block if even ordinary delegation is unsupported. Tool-call parallelism is not a prerequisite for background overlap, and source-level runtime capacity does not prove current tool permission.

The Router owns subsequent workflow decisions after Handler Results return. The Handler performs its delegated one-outcome work and returns a normalized Result; it does not select the next workflow action or manage coordination Todos.

### Todo cleanup lifecycle

This historical heading/anchor now owns one-way display derivation, replacement, and removal, not old-record cleanup admission. The Router may rebuild, replace, or clear the display from explicitly selected sources at coordination boundaries, including before handoff, wait, stop, or final report, without first proving old lifecycle eligibility. Old cancelled or unstarted items, missing/unapplied Results, same-name or conflicting display records, status regression, unresolved roles, current/active items, or outstanding dependencies/gates/confirmations must not block the display operation. Whole-group removal and full clear likewise require no child/container role closure. This does not satisfy those independent business predicates or authorize execution, cancellation, or Result adoption.

The Router must inspect the actual currently callable schema, description, and known contract for the chosen display operation. Tool names, package installation, or remembered source do not establish capability. The existing APIs below are usable when actually available; they are not new mandatory package dependencies:

| API | Actual display contract |
| --- | --- |
| `todo_set({tasks:[{name,todos:[{name,description}]}]})` | Replaces the whole display; no `status` input exists. Derive a new selected collection, not a lossless continuation of old records. `todo_set({tasks: []})` clears it. |
| `todo_transition({transitions:[{task,todo,status}]})` | Assigns `pending`, `in_progress`, `completed`, or `cancelled` by exact task/todo names. After set, use the new collection's unambiguous names to assign source-derived states, including explicit pending assignments when needed. Names select display targets, not execution identities. |
| `todo_remove({removals:[{task,todo}]})` or group target `{task}` | Removes an exact child, group, or disjoint mixed set while preserving non-target fields/order/status. Missing, duplicate, overlapping, or invalid targets reject the whole batch without mutation under this tool's atomic contract. Any native status may be removed; old lifecycle closure is not required. |
| `todo_view({})` | Returns the complete current display snapshot, not business completion or execution authority. |

Whole-view set followed by transition is normal source-based derivation, not a bypass. It must not be refused for lacking a cross-call transaction or for not preserving old survivor fields/statuses; neither CAS nor new tools are required. The Router must avoid ambiguous names in the newly selected set so actual transitions select the intended display items, without requiring stable old identities or an execution-ID scheme. Local removal, unlike whole-view replacement, must preserve non-targets and obey its actual selection/atomic-failure contract; unknown or ambiguous current targets require reporting the specific local tool limitation, not an old lifecycle audit.

| Native state | Source fact required |
| --- | --- |
| `pending` | Selected outcome is unstarted or not yet eligible for execution; do not infer a launch from an old label. |
| `in_progress` | Reliable actual active execution or current coordination action; an unconfirmed cancellation request does not establish cancelled execution. |
| `completed` | Reliable completed Result plus required outcome-completion evidence; gate release is judged separately. |
| `cancelled` | Explicit withdrawal/cancellation before launch with no later launch planned, or reliably confirmed cancellation of actual execution under the effective backend contract. Withdrawal of an unstarted outcome is not a claim that an active Handler was cancelled. |

Handler `partial`, `failed`, and `blocked` are not additional native statuses of these tools. The Router must retain them explicitly in descriptions or ordinary messages and use the closest truthful non-success native state, not invent a state or force completed. Reliable execution facts take precedence over UI labels. Missing Results may leave completion unknown or a non-success display, or the display may be cleared; no such choice permits completion inference or dependent release.

The Router must judge each tool return by its actual contract. If set succeeds but transition fails, report the confirmed new collection and the known partial alignment, not four-state completion. If a return/error leaves effects unknown, claim neither success nor no effect; use available observations and ordinary messages to expose what is known without blindly retrying, compensating, or restoring the old snapshot. Confirmed rejection is reported as such. A display capability gap, failure, or uncertain effect does not negate a reliable completed Result or block other independently satisfied admission/adoption predicates.

Display re-derivation must not repeat Result adoption or dependency release. Equivalent old notifications cannot replay removals or directly update a new same-name item; only reliable association to its selected source facts permits projection. Uncertain execution association still blocks that Result's adoption/release, not replacement or clearing of the display. Todo changes affect only the projection: they must not modify Work/Plan/Waves predicates or status to fit the UI, delete or alter Results, sessions, manifests, or artifacts, cancel real active tasks, or call `subagent_remove`. Necessary execution duties remain visible via existing ordinary messages; they are not a clear-before gate.

### Launch Evidence and Router Progression

Resolution, backend execution evidence, and Handler Result status are separate facts. The [Backend Adaptation Spec](backend-adaptation.md#1-inputs) defines the raw-return response: a pre-launch rejection has `resolution.status: blocked` and no `launch`; an attempted invocation retains resolved resolution plus `launch.tool` and exactly one of `rawReturn` or `rawError`. The Resolver does not produce a normalized `launch.status`, `taskId`, or `objective`. Backend fields inside raw evidence retain their backend-defined meaning; the Router interprets them only against the effective registered contract. A returned error envelope stays a return, an exception stays error evidence, and neither alone proves that no effects occurred. A missing or unusable Resolver response likewise cannot establish that no launch occurred; only an adoptable pre-launch blocked resolution proves no invocation. The Router retains available transport/backend evidence and treats unestablished effects as uncertain.

Before progression, the Router must inspect complete available launch evidence, establish the execution identity and relevant backend state, obtain and actually read the complete same-source Handler Result when available, correlate its scope/task/generation to the selected outcome using existing visible identity/state, and evaluate its status, required evidence, and material limitations. The [first-adoption reading contract](#first-adoption-and-later-excerpts) applies whether the backend initially returns full content or navigation; delivery and initial trusted reference issuance belong to the [Backend Adaptation Spec](backend-adaptation.md#21-result-delivery-and-protected-original-reading). A summary notification, resolved invocation, active launch, backend completion, or successful transport return alone cannot satisfy a work-completion predicate. Synchronous raw returns can contain a full Result, but the Resolver never adopts it on the Router's behalf. Uncertain identity/state/effects or missing, malformed, uncorrelatable, or conflicting Result evidence cannot manufacture a Handler status; retain the first established semantic state and report the limitation through existing visible surfaces.

| Evidence | Router-owned interpretation and progression |
| --- | --- |
| Pre-launch `resolution.status: blocked` | No launch attempted; record the precise admission block, not a Handler `blocked` Result. |
| Stable active identity and backend active-state evidence | Track active execution under the effective contract; do not complete work or release dependents. |
| Returned error, thrown error, or cancellation | Preserve the backend fact and known effects, distinct from Handler `failed`/`blocked`; do not infer absent effects or release dependents. |
| Missing/unusable Resolver response, ambiguous identity/state/effects, or unavailable full Result | Report uncertainty or the missing evidence; infer neither no launch nor completion, and leave the affected predicate unsatisfied without a fifth Handler Result status. |
| Safely correlated Handler `partial` | Preserve useful work and project `partial` truthfully; do not mark completed or release its dependents. |
| Safely correlated Handler `blocked` | Project `blocked` and its missing prerequisite truthfully; do not complete or release its dependents. |
| Safely correlated Handler `failed` | Project `failed` and attempted-failure evidence truthfully; do not complete or release its dependents. |
| Safely correlated Handler `completed` | Adopt the Result and communicate its facts truthfully; require completion evidence and applicable item/Wave predicates before release, independently of Todo mutation success. |
| Equivalent duplicate or conflicting/unusable Result | No repeated adoption or dependency release; fail closed for conflicting/unusable evidence. Re-derivation of established facts remains a separate display operation, never a same-name retarget. |

Uncertain evidence is not a Resolver outcome or a new Handler Result status. It blocks only the affected predicate and dependents; unrelated ready authorized work may proceed within existing conflict and backend limits. Todo terminal projection records the semantic Result, not proof that a Wave gate has passed: only `completed` plus required evidence satisfies an item predicate by default, and gate release additionally requires every listed item and the gate verification. No retry, fallback, polling, join/cancel/remove orchestration, scheduler, queue, or arbitrary-tool execution is added by this contract.

## 1.1 Generic single-result delegation contract

The Router must inspect the complete `objective`, `constraints`, and `deliverables` as one semantic bundle before performing any delegated outcome. One Handler invocation is valid only when all requested actions jointly establish one observable and verifiable terminal completion predicate. Internal checks, evidence collection, and intermediate actions may remain within that invocation when they are only means to establish that predicate and do not retain an independently valuable terminal state. A companion Skill must serve the same terminal predicate; companion status, action count, verb count, file count, or Skill count is never a decomposition rule.

The Router must decompose a request into separate Router-coordinated outcomes when any requested action has an independently meaningful completion boundary, including its own success or failure, an independently consumed Result or dependency, recovery or retry boundary, user-authorization or confirmation boundary, durable side effect, audit or compliance fact, persistent state change, or terminal state that is valuable to the Router or user independently of the parent result. One decisive independent boundary is sufficient; the rule does not require a fixed number of indicators. Multiple internal checks may remain one outcome when they share the same success, failure, retry/recovery, authorization, side-effect, audit, and terminal-state boundaries. Research is internal evidence when it only establishes the same implementation predicate; a research conclusion is a separate outcome when it is separately requested, retained, reviewed, or required as an independently consumed implementation dependency. For example, official Scoop identity/version/hash/mapping is internal evidence while implementing one predicate, but a requested or retained identity audit or independently consumed research conclusion is a separate outcome.

For delegated work the Router must follow these stages; the coordination strategy loading rule in section 1.3 precedes domain Skill selection when delegation is needed:

1. After the coordination strategy is available, identify and present each independently observable user-requested outcome and its completion predicate through the existing visible Todo or ordinary coordination message before selecting domain Skills, capability requests, Handoffs, or report packaging. A single user deliverable may depend on separately valuable A/B/C evidence branches: each independently consumable Result retains its own identity and state, while a final writer is one dependent outcome. Distinct user results remain distinct even when the final response combines their reports. Internal reproduction and checks for one bug, or alternatives supporting one comparison decision, remain one outcome when they share one terminal predicate.
2. Select one executable outcome, retaining its user-request correspondence and dependencies. Keep independent outcomes distinct even when their writes conflict; schedule such outcomes serially against the latest state.
3. Supply one closed `delegate: { name, params }` request to `resolve_delegation`. The Router must have established semantic eligibility first; Resolver validates structure, binds protected values exactly, and directly invokes the selected registered tool in the same call. The response preserves resolution and raw launch evidence together. Each outcome has its own ordered resolve-and-execute call; the fixed `handler` Agent, authorization, closed Handoff/admission schemas, and failure handling remain in force. Do not perform a hidden second outcome in one Handoff.
4. Receive and completely read the full Handler Result, correlate it to the selected outcome, and truthfully communicate its terminal facts through Todo descriptions/fields or ordinary messages before the next decision. Result adoption and evidence-gated dependency release do not depend on successful Todo mutation. A combined final report must not collapse independent execution or completion states.

Before delegation, the Router must inspect the complete Handoff bundle and reject a hidden multi-outcome Handoff before any outcome is performed. It must add dependency edges when an outcome requires another outcome's Result, input, authority, or valid execution, and serialize dependency or conflict edges. Background overlap is eligible only for independent, nonconflicting outcomes when the effective tool contract and available resources positively permit it; shared read-only sources alone do not defeat eligibility. Overlapping writes, ownership, authority, behavioral contracts, side effects, or dependencies do. Unknown or ambiguous capability requires serial scheduling within the actual tool contract, or blocking if ordinary delegation cannot be established. A branch whose identity is unresolved blocks only its own dependents, not unrelated ready branches.

After each atomic Handler Result, terminal delivery returns decision authority to the Router. The Handler must submit one complete YAML Result through an available completion channel (for Herdr, once as the `subagent_done.result` argument), without separately emitting that Result as a final message after successful submission; when the channel is unavailable it returns the YAML as its final response. A failed submission may be corrected and retried but cannot be claimed completed without acceptance. This changes no Result schema or backend lifecycle. The Router must read and reliably correlate the full Result, communicate `completed`, `partial`, `blocked`, or `failed` truthfully through the display or ordinary messages, and judge the applicable predicates before releasing dependents or scheduling another outcome; projection success is not an admission or adoption gate. A Handler must not choose continuation, collapse a non-completed Result into success, or release a dependency whose predicate is unsatisfied. Retry is scoped to the failed outcome's boundary; it must not silently replay completed durable side effects or independent outcomes. Irreversible or externally high-impact actions retain confirmation at the applicable action-executor boundary; generic Handler admission does not replace that confirmation.

### Handler failure without an adoptable Result

When a Handler terminates without an adoptable Result, the Router must read the complete failure state before choosing an action. It must preserve the distinctions among `partial`, `failed`, and `blocked` evidence and must not treat missing or unusable Result data as success.

After confirming that the failed execution is terminal and that the original atomic boundary remains valid, the Router should prefer resuming the same stable `subagentId` and failed `generation`. Resume-first keeps recovery within the original delegated outcome; it does not create a separate audit or retry outcome merely because the first execution produced no adoptable Result.

Resume is fail-closed. The Router must not resume when a terminal Result already exists, an active execution remains, the `subagentId`/`generation` association is uncertain, replay safety cannot be established, the atomic boundary or authority has changed, or user authorization is required again. In those cases, the Router must make a fresh decision appropriate to the evidence, such as auditing, asking for authorization or clarification, retrying as a new bounded outcome, or stopping. Any new outcome retains its own dependency, serialization, authorization, and atomicity rules.

Resume-first is Router judgment after failure evidence. It is not a hidden scheduler, queue, retry engine, fixed Result-to-action mapping, or Handler-owned continuation. A resume must never replay a completed durable side effect or an independently completed outcome.


Observable equivalent duplicate terminal signals must not repeat semantic Result adoption or dependency release. Malformed, structurally different, uncorrelatable, or conflicting signals fail closed for the affected outcome, preserve its first established semantic state, and do not satisfy or release its dependent predicates; report the limitation through existing visible surfaces. These rules do not prohibit independently re-deriving established facts or clearing the display, and do not permit an old notification to update a new same-name item without reliable source association. No fixed step, deliverable, file, phase, Skill, or Handler-call threshold, scheduler, queue, retry engine, continuation mechanism, or new persistence/identity infrastructure is introduced.

Examples are explanatory rather than classifiers: repairing several defects and reporting one conformance fact may be one outcome when the repairs are only evidence for that fact; a separate verification or audit fact after repair is a dependent outcome; staging and signing a commit are separate outcomes because each has durable, authorization, audit, and retry boundaries; and researching alternatives with one requested recommendation is one outcome when the research is supporting evidence rather than an independently requested terminal result.

## 1.2 Collaborative authority and layered delivery

This section governs requirement-to-implementation work. The Router owns communication, confirmation, outcome coordination, and continuation and applies the Skill-owned classification, admission-selection, and decomposition method in section 1.3; a Handler may analyze, document, plan, implement, or verify only its delegated single outcome. User agreement on intent, acceptance of normative wording, overview-route confirmation, and implementation-scope confirmation are distinct. Applicable PRD scope and ADR decisions constrain this Spec; Work, Context, and proposals do not establish authority. Neither the Resolver nor a Handoff establishes user authorization.

**C1. Settle intent before specifying new behavior.** For a new or materially changed requirement, the Router must use LLM analysis and communication with the user to settle intended outcomes, boundaries, constraints, and success criteria before treating them as authority. Material unanswered alternatives must be surfaced, not silently selected. Once intent is agreed, the applicable owning Spec must express verifiable behavior before the implementation plan is derived; reuse existing authority when it already expresses the behavior. Agreement must not be inferred from silence, a document's existence, a Handoff, or model readiness. Product or architectural changes require their owning PRD or ADR as applicable. Analysis, Spec work, and initial planning are preparation, not implementation; they use standalone admission within the preparation boundary below without requiring the tuple they are preparing or confirmation of an implementation plan. Explicit authority-writing permission is still required. This sequence creates no separate approval round for every preparatory result or document. For durable behavior changes or accepted architectural or governance changes, the Router must also satisfy the [visible authority assessment](#visible-authority-assessment) before deriving the dependent implementation plan.

**C2. Plan by delivery scope.** One Spec may support several implementation plans. A simple coherent deliverable may have one implementation plan and no overview. Plan boundaries must follow meaningful verifiable outcomes and dependencies or key decisions, not file, Spec, task, template, or Handler-call counts.

**C3. Confirm the route separately for complex delivery.** Before any stage executes, complex delivery must have an overview showing stages, dependencies, and incremental outcomes. The Router must substantively show that route and obtain explicit user confirmation of its direction and staging. This confirms only the route, not execution of any stage. Detail a stage's implementation plan when its authority and evidence are sufficient; future-stage details may remain deferred if they do not invalidate the route or the current stage. An overview must not hide a material decision needed for the current stage. Each implementation plan must identify its Spec-derived scope and relationship to the overview, if any. Multiple Plan/Waves pairs may share one Work; each new planned invocation selects exactly one explicit same-directory Work/Plan/Waves tuple under section 2. An overview is not an executable plan merely because of its name or path. Waves need only be ready for the selected planned invocation, not every future stage; section 1's visible coordination obligation for identified outcomes still applies.

**C4. Disclose and confirm each implementation scope.** Before executing an implementation plan, the Router must communicate its scope, intended outcome and important exclusions; proposed behavior or artifact changes and affected ownership boundaries; execution steps and material dependencies; verification and completion criteria; and important tradeoffs, risks, and key decisions. Links or paths may supplement but must not replace that disclosure. The Router must obtain explicit current-user confirmation corresponding to the disclosed implementation scope. Overview approval, agreement on intent, Spec readiness, document status, a Handoff, silence, and successful Resolver admission do not substitute. Absent, declined, or ambiguous confirmation blocks the affected implementation until resolved by ordinary user communication. Approval of one plan does not authorize another derived from the same Spec.

**C5. Execute autonomously inside confirmed scope.** The Router and its bounded Handlers must decompose or refine current-scope Waves items, implement, repair in-scope defects, and verify without seeking approval for each item, file, check, or Handler invocation. The selected Waves document is an executable current-scope input, not a separate user approval gate. A plan may span several single-result Handlers; the Router must still make the next workflow decision after each Result under section 1.1.

**C6. Stop at substantive changes.** Before executing a changed portion that materially alters the authorized outcome, behavior, deliverable, success criterion, key architecture, consequential dependency, risk, or verification, the Router must explain what changed, why, and its impact, then obtain explicit confirmation of that changed portion. If a finding invalidates authority, reconcile it at its owning boundary before dependent execution; this rule does not independently authorize editing that authority. Unchanged confirmed work does not need reapproval. Task refinement, in-scope repair, or non-substantive edits do not alone require renewed confirmation. Current-call byte drift under section 3 can still fail closed as a legality check; drift alone does not prove missing user approval. The Router assesses substantive impact when deciding whether to re-disclose and reconfirm.

**C7. Verify and report.** Compare delivered behavior with applicable authority and, when present, the confirmed implementation plan using actual evidence. Report partial or failed verification truthfully. Correct and re-verify within scope autonomously; if correction changes the authorized boundary, apply C6.

**C8. Direct restoration.** Under existing explicit authorization, a bounded defect repair may proceed without a new Spec or implementation-plan confirmation only to restore already-authoritative behavior. Identify the authority and observed divergence, run in-scope tests and verification against it, and report the outcome. Ambiguous target authority requires clarification before classifying the repair. New behavior, a changed key decision, consequential architecture or dependency, or expanded scope must follow C1-C4, or C6 within a confirmed plan, before that changed portion executes.

**C9. Minimum incident containment.** During an active security, data-loss, or availability incident, an agent may take the minimum scoped action under existing authorization needed to limit ongoing harm even if normal planning or authority updates cannot precede containment. Record the bounded exception, verify its effect as far as practicable, report it as temporary, and reconcile applicable authority afterward. Containment does not resolve the root cause or authorize redesign, permanent new behavior, or a wider repair; follow-on work needs its own authority, plan disclosure, and confirmation. Destructive or externally high-impact actions retain their applicable action-executor authorization boundary even in an incident.

**C10. Behavior-neutral maintenance.** Small maintenance preserving already-authoritative behavior may proceed under existing explicit authorization without a new Spec or implementation-plan confirmation. Verify unchanged behavior with focused checks and report the result. Material changes in behavior, scope, architecture, dependency, or risk follow C1-C4 or C6 within a confirmed plan; material ambiguity requires clarification before work. Standalone admission under section 2 establishes only legality, not that authorization exists. C8-C10 do not themselves grant permission, establish a new approval round, or confirm an overview or implementation plan.

### Clear user-facing questions

For Router-authored user-facing questions, explanations, and options, including caller-authored `ask` content, the Router must first state the actual problem and its relationship to the user's goal, then explain why this step is needed now and why a user decision is needed. It must explain the practical effects of the offered choices and give a recommendation when supported by evidence; otherwise it must state the uncertainty rather than invent a recommendation. When the context already makes the connection clear, a brief reference is sufficient; this contract requires neither a rigid long template nor repeated background.

The Router must explain necessary unfamiliar terms before using them to frame a decision. Internal identifiers, stage names, and status codes must not substitute for the actual problem or serve as the question's subject; necessary identifiers may supplement the explanation afterward for traceability. Clear expression must retain important risks, backend execution identity, and necessary tracking evidence. This contract governs content the Router writes, not tool-generated metadata; it does not require metadata hiding, tool-schema or UI changes, or evidence removal.

Under C5, routine steps within already confirmed scope must not be repackaged as repeated choice or approval questions; ordinary progress need not become a question. Substantive permission, scope, risk, or important tradeoff decisions must still explain their effects and obtain the confirmation required by C4, C6, and the applicable action-executor boundary. These expression obligations do not grant authorization, change roles or admission, alter execution/confirmation flow, or create a new confirmation mechanism; they do not qualify new output behavior as C10 behavior-neutral maintenance.

### Visible authority assessment

Under [ADR-0010](../adr/0010-visible-authority-assessment-and-conditional-sdd.md#decision), before deriving a dependent implementation plan for a durable behavior change or accepted architectural or governance change, the Router must visibly account for each of PRD, ADR, and Spec. An existing coordination explanation or bounded assessment Result must state each family's action, owning boundary, existing or intended path, and one sentence giving an evidence-backed reason. Non-applicability must be explained rather than omitted.

| Action | Required meaning |
| --- | --- |
| `reuse` | Existing authority adequately covers the settled scope; identify its owner and path. |
| `update` | The same owner or decision identity needs amendment; identify the material gap and owning path. |
| `create` | Required authority is missing, or an accepted ADR decision has a distinct lifecycle; identify the owner and intended output path. |
| `skip` | The family needs no change or is not applicable to the bounded scope; give the owner/boundary and path where known and a bounded reason. |
| `blocked` | Required coverage, ownership, evidence, permission, or intent cannot be established; identify the unresolved gap and block dependent planning. |

Unknown ownership or a path that cannot yet be determined must be reported as unresolved, not invented. An intended new output path is a declared target, not an existing artifact or readable input reference. The assessment establishes coverage and handling, not authority-writing permission or implementation confirmation. Required reconciliation must be complete before dependent planning uses the changed authority; an unsettled material question must return to Router-owned clarification rather than become normative behavior.

The Router may reuse a sufficiently reliable assessment that still covers the current scope, decisions, owners, and relevant authority versions. Material scope or authority changes, contradictory evidence, or important coverage uncertainty require reassessment of the affected portion only. Neither every delivery stage nor every Handler invocation requires a fresh assessment or SDD reread. No separately persisted assessment artifact, new Result field, schema, approval round, loaded-state receipt, registry, or CAS mechanism is required. Coverage is not measured by SDD invocation or new-ADR counts.

The [conditional SDD selection contract](skill-library.md#conditional-authority-first-method) applies when authority is missing, false, materially incomplete, or subject to an important unresolved coverage question. Settled evidence may support direct entry to a known narrow owning writer; direct entry does not waive this assessment, authority, or authorization obligations. For the same ADR decision identity, writers must reuse and, if amendment is required, update the existing owner; only a distinct accepted decision lifecycle permits a new ADR. An unaccepted choice must not be recorded as an accepted ADR.

C8-C10 retain their narrow existing-authorization exceptions: a focused, evidence-backed `reuse` or `skip` remains possible without a new ADR, Spec, or Plan on every repair or maintenance change. Material ambiguity or new behavior must not be disguised as maintenance. Initial assessment, explicitly authorized authority writing, and first Work/Context/Plan/Waves preparation retain standalone admission within the [preparation boundary](#preparation-boundary), without requiring their future tuple as input. A durable classification or SDD selection alone does not force planned admission; selected graph-bound work retains its planned prerequisites. This amendment does not require reauthorization of unchanged confirmed implementation.

Verification must stay within the same preparation boundary. These preparation exclusions do not prohibit an independently authorized standalone change that satisfies its own applicable authority and permission requirements. A domain Skill name, companion Skill, accepted document status, or loaded strategy must not widen permissions.

Initial Work/Context/Plan/Waves preparation must not depend on those future outputs already being readable. Declare missing output paths in the Handoff objective, constraints, deliverables, or inline context; do not encode them as `context[].ref` or planned authority selectors. Every actual reference still must exist and be readable. Existing authority and available evidence are inputs; the prepared linked tuple becomes a planned implementation input only after it exists and satisfies the planned-work contract.

A completed preparation Result establishes only its bounded preparation predicate. The Router must still disclose later runtime changes and the substantive implementation scope and obtain explicit current-user confirmation under C3-C4 when applicable before implementation. Intent agreement, accepted authority wording, prepared files, successful standalone admission, or Result `completed` cannot substitute. C8-C10 retain their existing authorization and legality boundaries; the standalone rename and preparation category add no receipt, approval round for every preparatory artifact, or automatic transition into implementation.

### New planned-work document and release contract

For new planned implementation, `work.md` identifies the delivery objective; a selected Plan defines one Spec/ADR-derived implementation scope; its Waves document defines the executable decomposition of that scope. These documents are derived work inputs, not product or technical authority. The Plan must explicitly link its Work and exactly one corresponding Waves document; Waves must explicitly link that same Plan and Work and identify which Plan outcome its gates establish. The selected Plan and Waves must be direct members of the same `docs/works/<work-slug>/` directory as `work.md`; neither a directory listing nor an overview infers an executable tuple. The unsliced pair is `plan.md`/`waves.md`. Sliced direct members follow the existing Plan-member grammar with `waves` replacing `tasks`: optional `<prefix>--`, then `plan` or `waves`, then optional `-<slice>`, then `.md`; the pair must have the same prefix and slice. A selected invocation identifies exactly one pair, even when one Work contains several pairs.

The Plan must state its scope, intended outcome, exclusions, authority, verification, and which Wave gates are required for its completion. Each Wave must have a stable unique identifier, an incremental outcome, a non-empty set of item identifiers, explicit predecessor Wave gates (if any), and a verifiable release predicate. Each item must have a stable unique identifier, bounded scope and intended effects, one independently observable completion predicate with verification evidence, and explicit prerequisite item identifiers (if any). Wave and item references must resolve within the selected Waves document; identifiers must not duplicate, prerequisite links must be acyclic, and no gate may depend on its own release. Display order or a heading alone does not create a dependency. Internal checks that have no independent Result remain part of an item rather than becoming separate items. Within explicitly selected display scope, the Router must represent each independently observable outcome once through Todo projection or ordinary coordination messages; grouping outcomes in a Wave does not merge their Results.

An item becomes eligible only when its prerequisite predicates and its containing Wave's prerequisite gates are satisfied, the selected implementation scope remains confirmed and authoritative, and conflicts and effective delegate-tool constraints permit the action. The Waves document must make known dependencies and write, ownership, authority, behavioral-contract, and side-effect conflicts visible; conflicting items serialize against the latest state even if they are otherwise independent. Shared read-only inputs do not conflict. Unknown conflict or capability evidence cannot justify overlap; use a safe serial path or block when legality cannot be established. Independent ready items and Waves with no dependency or conflict may progress under the effective tool contract; neither Wave numbering nor document order forces an unstated barrier.

A Wave gate releases only its explicitly dependent work, and only after every item listed in that Wave satisfies its completion predicate and the gate's stated verification passes. A Handler returns exactly one Result for its bounded outcome: `completed`, `partial`, `failed`, or `blocked`. Only `completed` plus required evidence satisfies its item predicate by default; `partial` preserves useful work but does not complete or release it, and `failed` or `blocked` also do not release dependents. An item or gate without an adoptable Result or sufficient evidence remains unsatisfied. The Router must read and reliably correlate each complete Result, communicate its truthful terminal facts through Todo fields/descriptions or ordinary messages, and judge gate release independently of Todo mutation success, making a fresh decision after each Result; unrelated ready work may continue. Changing a predicate, accepting partial evidence in place of a required completion, or bypassing a gate requires the applicable authority and C6 scope decision, not a status reinterpretation or implicit waiver. Missing items, contradictory predicates, unresolved dependencies, cycles, or an uncheckable gate block the affected planned execution until corrected and, when substantive, reconfirmed. Waves is an executable document for human/Router coordination, **not an automatic scheduler**, queue, retry engine, approval service, additional Handler Result, or new backend/tool contract.

Migration is explicit: new planned work uses Work/Plan/Waves, not a newly authored Tasks layer. Existing completed Work/Plan/Tasks artifacts remain historical records and must not be silently rewritten, renamed, or retroactively invalidated. An unfinished old Plan/Tasks scope must be explicitly migrated to a linked Work/Plan/Waves tuple and reconciled with its applicable authority and user confirmation before further planned implementation; old Tasks must not be silently interpreted as Waves. Historical Tasks-only Resolver acceptance does not establish conformance for a new Waves plan. The inspected source candidate now includes Waves-aware admission, but live registration and bootstrap remain unverified. Standalone admission and the narrow C8-C10 exceptions remain separately governed.

Confirmation remains Router-owned ordinary interaction. No receipt, token, approval registry, authorization storage, or new Handler Result schema is introduced. Irreversible or externally high-impact actions retain their action-executor authorization boundary independently of plan confirmation.

## 2. Handoff and admission input

A Handoff contains `objective`, `primarySkill`, optional `companionSkills`, `context`, optional `constraints`, and optional `deliverables`. Each context item must contain exactly one non-empty readable `ref` or one non-empty `inline` value plus a non-empty `purpose`.

Admission has exactly two alternatives, standalone and planned. Each invokes one Handler for one terminal predicate under section 1.1; neither path changes the Handoff fields or grants permission.

### Standalone admission

The closed standalone alternative is `admission: { path: "standalone", basis: string[], verification: string[] }`. It must contain exactly `path`, `basis`, and `verification`; both arrays must be non-empty and every entry must be a non-empty string, including rejection of whitespace-only entries. `basis[]` must describe the authorized non-tuple outcome, applicable authority or settled intent, and bounded intended effects. `verification[]` must describe focused checks of the same terminal predicate within its permission boundary. This prose records the Router's basis; it is neither a receipt nor Resolver evidence of user authorization. The original atomic basis/verification validation is retained; eligibility expands beyond small behavior-neutral maintenance.

Standalone covers work not bound to an executable graph: read-only investigation; explicitly authorized PRD/ADR/Spec writing; initial Work/Context/Plan/Waves preparation; and a bounded independent change where applicable authority and authorization permit it. Complexity or size alone does not require planned admission. Conversely, one selected graph item or implementation that requires the planned-work prerequisites must use planned; a missing tuple, dependency, gate, or required confirmation is a block, not standalone eligibility. C1-C10 continue to govern authority and implementation confirmation. Preparation is restricted by section 1.2's preparation effect boundary, while other standalone effects retain their own authorization; schema acceptance does not classify them.

Standalone must pass ordinary closed Handoff, Skill, actual-reference, root capability, candidate, delegate, and protected-binding validation. It must not accept an `authority` selector or require an existing Work/Plan/Waves tuple, selected-tuple document bytes, or planned current-call/JIT subject checks. Readable Work/Plan/Waves documents may be ordinary context evidence; their presence alone does not bind an outcome to the executable graph. It must not accept output selectors, acceptance, receipt, digest, reviewer, session, activation, or other unsupported fields. Future output targets belong in the ordinary Handoff text or inline context; every actual `context[].ref` still must be readable. The Router and loaded strategy own semantic eligibility and effects; the Resolver must not classify effects or interpret authorization from `basis[]`.

When runtime validation is reached, malformed standalone structure or unknown fields must return `invalid_admission`; empty, non-array, non-string, empty-string, or whitespace-only basis/verification arrays must retain the existing `invalid_atomic_basis` code. An unreadable actual Handoff reference retains `invalid_reference`. Closed tool-schema rejection may occur before Resolver runtime validation; it must prevent launch without fabricating a Resolver response. The legacy error name is intentionally retained, as explained in section 4.

### Planned admission

The closed planned alternative is `admission: { path: "planned", authority: { work, plan, waves } }`; it must contain exactly `path` and `authority`, whose only fields are non-empty string selectors `work`, `plan`, and `waves`. For new planned work, admission selects one same-directory `work.md` and an explicitly linked matching Plan/Waves pair under section 1.2; `tasks` is not a synonym for `waves`. The selected three distinct canonical paths must occur exactly once as Handoff reference context. The direct-member tuple grammar (with Waves replacing Tasks for new plans), canonical path rules, canonical document-byte rules, canonical JSON rules, and normalized Handoff hashing remain current-call legality inputs. The Router confirms reciprocal Plan/Waves links and semantic item/gate readiness; the Resolver validates structural selectors, canonical paths and current bytes, tuple membership and matching member names, and rejects drift. It does not grant confirmation, schedule Waves, or decide whether a predicate is substantively met. The inspected source candidate now implements closed Work/Plan/Waves selectors and rejects Tasks-only selectors; focused source verification is recorded in the migration Context. This does not establish installed-runtime freshness or live bootstrap.

Model input must not supply receipt, acceptance, reviewer, session, activation, digest, or other capability-shaped fields. The Resolver derives identities from filesystem bytes and supplied structure; it never trusts model-supplied identity fields.
