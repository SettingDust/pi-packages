## 1. Boundary and trust ownership

The Router/coordinator owns workflow confirmation. For planned implementation it must complete the Plan and Tasks applicable to the selected ready scope, disclose the substantive plan and exact authority in an ordinary message, obtain explicit current-user confirmation of that scope, and then invoke delegation. Preparatory analysis, Spec reconciliation, and planning do not inherit an implementation-plan confirmation requirement; their own authority and admission requirements still apply. Section 1.2 defines the workflow and narrow existing-authorization exceptions. A Handoff requests work and never proves acceptance. `@settingdust/pi-harness` does not authenticate the user, interpret natural-language confirmation, persist confirmation, issue a token or receipt, or replay-protect confirmation history.

The Harness Extension owns prompt/tool registration and resolver execution. The Resolver validates and resolves; it must not interact, disclose, activate a Plan, issue a receipt, or launch a Handler.
The Router's coordination Todo records are a main-session workflow projection, not Handler input, Resolver state, backend lifecycle state, or a persistent task database. For multi-step work, the Router must create the complete coordination set immediately, with exactly one item per independently observable outcome. It must project the current item as `in_progress` immediately before each coordination action, record each terminal Handler Result truthfully immediately after notification, release dependencies only after that semantic terminal update, and then schedule newly unblocked work. It must use native task status and fields when they express the needed fact; otherwise it must preserve the closest truthful native status and encode the semantic fact in existing descriptions or subjects, or in an ordinary Router coordination message. Total absence of any writable and visible coordination mechanism may block coordination; lack of an exact runtime schema must not.

Todo lifecycle state is semantic and deterministic: an unstarted outcome is pending; an outcome whose coordination action is about to run is in_progress; and Result `completed`, `partial`, `failed`, or `blocked` maps to the matching truthful terminal projection when the environment exposes that state, otherwise to the closest truthful native status plus existing descriptive/message surfaces. The Result status remains retained as data and must not be collapsed into success or used as a workflow-control field. Never mark completed for partial, failed, or blocked, and never delete active or unresolved work. A terminal Todo is stale only when the available environment can establish that its terminal Result was applied, no active or unresolved dependent outcome still requires the record, it is not the current coordination item, and all required fields are known and non-contradictory. An orphan duplicate additionally requires an observable matching identity and non-canonical identity. Age alone, pending, in_progress, unknown identity, or an unresolved dependency never makes a Todo stale. If the environment cannot establish safe stale detection or deletion, retain the record and report the limitation.

The Router must adapt to the current environment's visible coordination mechanism. Its capability observation records which native statuses and fields are available, and whether any writable/visible mechanism exists; this observation is not a requirement for an exact `TaskCreate`/`TaskUpdate` schema. Only total absence of such a mechanism blocks the coordination flow.
The Router correlates a Handler Result using existing task/runtime identity and visible fields/messages available in the environment. When an identity and equivalent visible Result are available, a duplicate or resent terminal notification is idempotent and produces no second terminal Todo update or repeated dependency release. When an incoming Result is malformed or conflicts with an already applied observable identity, the Router fails closed, preserves the first semantic outcome, leaves status and dependency projection unchanged, and reports the conflict through an existing description, subject, or ordinary Router coordination message. It must not require persistent identity/generation storage, canonical digest storage, restart/outbox APIs, or an exact description mutation. After restart, resume, or replay, it may reapply a notification only when the available identity and visible state make that safe; otherwise it retains the Todo and reports the limitation.

The Router may use parallel resolve-to-spawn chains only for independently verifiable outcomes without conflicting inputs, outputs, writes, ownership, authority, behavioral contracts, or side effects, and only when the current Host/tool-call capability is positively proven. Shared read-only inputs alone do not conflict. Unsupported, stale, incompatible, or ambiguous Host capability requires serial scheduling. Dependencies and conflicting writes (including independent outcomes writing the same file) or other boundaries require serialization even when parallel capability is available.

The Router owns subsequent workflow decisions after Handler Results return. The Handler performs its delegated one-outcome work and returns a normalized Result; it does not select the next workflow action or manage coordination Todos.

## 1.1 Generic single-result delegation contract

The Router must inspect the complete `objective`, `constraints`, and `deliverables` as one semantic bundle before performing any delegated outcome. One Handler invocation is valid only when all requested actions jointly establish one observable and verifiable terminal completion predicate. Internal checks, evidence collection, and intermediate actions may remain within that invocation when they are only means to establish that predicate and do not retain an independently valuable terminal state. A companion Skill must serve the same terminal predicate; companion status, action count, verb count, file count, or Skill count is never a decomposition rule.

The Router must decompose a request into separate Router-coordinated outcomes when any requested action has an independently meaningful completion boundary, including its own success or failure, an independently consumed Result or dependency, recovery or retry boundary, user-authorization or confirmation boundary, durable side effect, audit or compliance fact, persistent state change, or terminal state that is valuable to the Router or user independently of the parent result. One decisive independent boundary is sufficient; the rule does not require a fixed number of indicators. Multiple internal checks may remain one outcome when they share the same success, failure, retry/recovery, authorization, side-effect, audit, and terminal-state boundaries. Research is internal evidence when it only establishes the same implementation predicate; a research conclusion is a separate outcome when it is separately requested, retained, reviewed, or required as an independently consumed implementation dependency. For example, official Scoop identity/version/hash/mapping is internal evidence while implementing one predicate, but a requested or retained identity audit or independently consumed research conclusion is a separate outcome.

For delegated work the Router must follow four phases:

1. Identify and present each independently observable user-requested outcome and its completion predicate through the existing visible Todo or ordinary coordination message before selecting Skills, capability requests, Handoffs, or report packaging. Distinct user results remain distinct even when the final response combines their reports. Internal reproduction and checks for one bug, or alternatives supporting one comparison decision, remain one outcome when they share one terminal predicate.
2. Select one executable outcome, retaining its user-request correspondence and dependencies. Keep independent outcomes distinct even when their writes conflict; schedule such outcomes serially against the latest state.
3. Resolve that outcome's exact one-result Handoff and, on a `resolved` response and compatible delegate capability, launch its Handler with the exact resolved prompt, model, and thinking as the next environment action. Each selected outcome has its own resolve-to-spawn chain; the fixed `handler` Agent, authorization, closed Handoff/admission schemas, and failure handling remain in force. Do not perform a hidden second outcome in its Handoff.
4. Receive the full Handler Result, correlate it to the selected outcome and truthfully project its terminal state before deciding on further work or releasing dependents. A combined final report must not collapse independent execution or completion states.

Before delegation, the Router must inspect the complete Handoff bundle and reject a hidden multi-outcome Handoff before any outcome is performed. It must add dependency edges when an outcome requires another outcome's Result, input, authority, or valid execution, and serialize dependency or conflict edges. Concurrent delegation is eligible only for independent, nonconflicting outcomes when current Host/tool-call capability is positively proven; shared read-only sources alone do not defeat eligibility, while overlapping writes, ownership, authority, behavioral contracts, side effects, or dependencies do. Unknown or ambiguous capability requires serial scheduling.

After each atomic Handler Result, terminal delivery returns decision authority to the Router. The Handler must submit one complete YAML Result through an available completion channel (for Herdr, once as the `subagent_done.result` argument), without separately emitting that Result as a final message after successful submission; when the channel is unavailable it returns the YAML as its final response. A failed submission may be corrected and retried but cannot be claimed completed without acceptance. This changes no Result schema or backend lifecycle. The Router must read the full Result, truthfully project `completed`, `partial`, `blocked`, or `failed`, and make a fresh decision before releasing dependents or scheduling another outcome. A Handler must not choose continuation, collapse a non-completed Result into success, or release a dependency whose predicate is unsatisfied. Retry is scoped to the failed outcome's boundary; it must not silently replay completed durable side effects or independent outcomes. Irreversible or externally high-impact actions retain confirmation at the applicable action-executor boundary; generic Handler admission does not replace that confirmation.

### Handler failure without an adoptable Result

When a Handler terminates without an adoptable Result, the Router must read the complete failure state before choosing an action. It must preserve the distinctions among `partial`, `failed`, and `blocked` evidence and must not treat missing or unusable Result data as success.

After confirming that the failed execution is terminal and that the original atomic boundary remains valid, the Router should prefer resuming the same stable `subagentId` and failed `generation`. Resume-first keeps recovery within the original delegated outcome; it does not create a separate audit or retry outcome merely because the first execution produced no adoptable Result.

Resume is fail-closed. The Router must not resume when a terminal Result already exists, an active execution remains, the `subagentId`/`generation` association is uncertain, replay safety cannot be established, the atomic boundary or authority has changed, or user authorization is required again. In those cases, the Router must make a fresh decision appropriate to the evidence, such as auditing, asking for authorization or clarification, retrying as a new bounded outcome, or stopping. Any new outcome retains its own dependency, serialization, authorization, and atomicity rules.

Resume-first is Router judgment after failure evidence. It is not a hidden scheduler, queue, retry engine, fixed Result-to-action mapping, or Handler-owned continuation. A resume must never replay a completed durable side effect or an independently completed outcome.


Observable equivalent duplicate terminal signals are idempotent. Malformed, structurally different, uncorrelatable, or conflicting signals fail closed, preserve the first established semantic state, do not update status or release or schedule dependencies, and report the limitation through existing visible surfaces. This contract introduces no fixed step, deliverable, file, phase, Skill, or Handler-call threshold, and implies no scheduler, queue, retry engine, continuation mechanism, or new persistence or identity infrastructure.

Examples are explanatory rather than classifiers: repairing several defects and reporting one conformance fact may be one outcome when the repairs are only evidence for that fact; a separate verification or audit fact after repair is a dependent outcome; staging and signing a commit are separate outcomes because each has durable, authorization, audit, and retry boundaries; and researching alternatives with one requested recommendation is one outcome when the research is supporting evidence rather than an independently requested terminal result.

## 1.2 Collaborative authority and layered delivery

This section governs requirement-to-implementation work. The Router owns communication, confirmation, decomposition, and continuation; a Handler may analyze, document, plan, implement, or verify only its delegated single outcome. User agreement on intent, acceptance of normative wording, overview-route confirmation, and implementation-scope confirmation are distinct. Applicable PRD scope and ADR decisions constrain this Spec; Work, Context, and proposals do not establish authority. Neither the Resolver nor a Handoff establishes user authorization.

**C1. Settle intent before specifying new behavior.** For a new or materially changed requirement, the Router must use LLM analysis and communication with the user to settle intended outcomes, boundaries, constraints, and success criteria before treating them as authority. Material unanswered alternatives must be surfaced, not silently selected. Once intent is agreed, the applicable owning Spec must express verifiable behavior before the implementation plan is derived; reuse existing authority when it already expresses the behavior. Agreement must not be inferred from silence, a document's existence, a Handoff, or model readiness. Product or architectural changes require their owning PRD or ADR as applicable. Analysis, Spec work, and planning are preparation, not implementation; they may be delegated under their applicable authority and admission rules without first obtaining confirmation of an implementation plan. This sequence creates no separate approval round for every preparatory result or document.

**C2. Plan by delivery scope.** One Spec may support several implementation plans. A simple coherent deliverable may have one implementation plan and no overview. Plan boundaries must follow meaningful verifiable outcomes and dependencies or key decisions, not file, Spec, task, template, or Handler-call counts.

**C3. Confirm the route separately for complex delivery.** Before any stage executes, complex delivery must have an overview showing stages, dependencies, and incremental outcomes. The Router must substantively show that route and obtain explicit user confirmation of its direction and staging. This confirms only the route, not execution of any stage. Detail a stage's implementation plan when its authority and evidence are sufficient; future-stage details may remain deferred if they do not invalidate the route or the current stage. An overview must not hide a material decision needed for the current stage. Each implementation plan must identify its Spec-derived scope and relationship to the overview, if any. Multiple Plan/Tasks pairs may share one Work; each planned invocation still selects exactly one explicit same-directory Work/Plan/Tasks tuple under section 2. An overview is not an executable plan merely because of its name or path. Tasks need only be ready for the selected planned invocation, not every future stage; section 1's visible coordination obligation for identified outcomes still applies.

**C4. Disclose and confirm each implementation scope.** Before executing an implementation plan, the Router must communicate its scope, intended outcome and important exclusions; proposed behavior or artifact changes and affected ownership boundaries; execution steps and material dependencies; verification and completion criteria; and important tradeoffs, risks, and key decisions. Links or paths may supplement but must not replace that disclosure. The Router must obtain explicit current-user confirmation corresponding to the disclosed implementation scope. Overview approval, agreement on intent, Spec readiness, document status, a Handoff, silence, and successful Resolver admission do not substitute. Absent, declined, or ambiguous confirmation blocks the affected implementation until resolved by ordinary user communication. Approval of one plan does not authorize another derived from the same Spec.

**C5. Execute autonomously inside confirmed scope.** The Router and its bounded Handlers must decompose or refine current-scope Tasks, implement, repair in-scope defects, and verify without seeking approval for each task, file, check, or Handler invocation. Tasks required by planned admission remain current-scope inputs, not a separate user approval gate. A plan may span several single-result Handlers; the Router must still make the next workflow decision after each Result under section 1.1.

**C6. Stop at substantive changes.** Before executing a changed portion that materially alters the authorized outcome, behavior, deliverable, success criterion, key architecture, consequential dependency, risk, or verification, the Router must explain what changed, why, and its impact, then obtain explicit confirmation of that changed portion. If a finding invalidates authority, reconcile it at its owning boundary before dependent execution; this rule does not independently authorize editing that authority. Unchanged confirmed work does not need reapproval. Task refinement, in-scope repair, or non-substantive edits do not alone require renewed confirmation. Current-call byte drift under section 3 can still fail closed as a legality check; drift alone does not prove missing user approval. The Router assesses substantive impact when deciding whether to re-disclose and reconfirm.

**C7. Verify and report.** Compare delivered behavior with applicable authority and, when present, the confirmed implementation plan using actual evidence. Report partial or failed verification truthfully. Correct and re-verify within scope autonomously; if correction changes the authorized boundary, apply C6.

**C8. Direct restoration.** Under existing explicit authorization, a bounded defect repair may proceed without a new Spec or implementation-plan confirmation only to restore already-authoritative behavior. Identify the authority and observed divergence, run in-scope tests and verification against it, and report the outcome. Ambiguous target authority requires clarification before classifying the repair. New behavior, a changed key decision, consequential architecture or dependency, or expanded scope must follow C1-C4, or C6 within a confirmed plan, before that changed portion executes.

**C9. Minimum incident containment.** During an active security, data-loss, or availability incident, an agent may take the minimum scoped action under existing authorization needed to limit ongoing harm even if normal planning or authority updates cannot precede containment. Record the bounded exception, verify its effect as far as practicable, report it as temporary, and reconcile applicable authority afterward. Containment does not resolve the root cause or authorize redesign, permanent new behavior, or a wider repair; follow-on work needs its own authority, plan disclosure, and confirmation. Destructive or externally high-impact actions retain their applicable action-executor authorization boundary even in an incident.

**C10. Behavior-neutral maintenance.** Small maintenance preserving already-authoritative behavior may proceed under existing explicit authorization without a new Spec or implementation-plan confirmation. Verify unchanged behavior with focused checks and report the result. Material changes in behavior, scope, architecture, dependency, or risk follow C1-C4 or C6 within a confirmed plan; material ambiguity requires clarification before work. Atomic admission under section 2 establishes only legality, not that authorization exists. C8-C10 do not themselves grant permission, establish a new approval round, or confirm an overview or implementation plan.

Confirmation remains Router-owned ordinary interaction. No receipt, token, approval registry, authorization storage, or new Resolver/Handoff/Result schema is introduced. Irreversible or externally high-impact actions retain their action-executor authorization boundary independently of plan confirmation.

## 2. Handoff and admission input

A Handoff contains `objective`, `primarySkill`, optional `companionSkills`, `context`, optional `constraints`, and optional `deliverables`. Each context item must contain exactly one non-empty readable `ref` or one non-empty `inline` value plus a non-empty `purpose`.

Atomic admission remains available for one small, behavior-neutral change with non-empty bounded `basis[]` and focused `verification[]`. Planned admission selects exactly one same-directory `work.md` plus either matching `plan.md`/`tasks.md` or matching sliced members. The selected three canonical paths must occur exactly once as Handoff reference context. The tuple grammar, canonical path rules, canonical document-byte rules, canonical JSON rules, and normalized Handoff hashing remain current-call validation inputs.

Model input must not supply receipt, acceptance, reviewer, session, activation, digest, or other capability-shaped fields. The Resolver derives identities from filesystem bytes and supplied structure; it never trusts model-supplied identity fields.

## 3. Planned validation without authorization state

For planned admission, the Resolver must:

1. validate the ordinary Handoff, Skills, root capability request, references, and admission shape;
2. canonicalize and validate the selected Work/Plan/Tasks tuple;
3. read the selected authority as required for current-call validation and derive canonical paths, bytes, and normalized Handoff identities;
4. run the configured final current-call/JIT recomputation immediately before returning a resolved invocation; and
5. return a resolved invocation when those checks pass, without looking up or inserting acceptance state.

The Resolver remains non-interactive. No planned call waits for, invokes, or checks a Plan activation boundary. For planned implementation, the Router must perform the selected scope's confirmation before invoking this delegation path; that workflow obligation is outside the Resolver contract and cannot be represented by a receipt. Preparatory delegations and the section 1.2 exceptions retain their own authorization boundaries; a successful planned or atomic resolve never supplies authorization.

If authority or Plan bytes change between current-call observations, the call must fail closed with `authority_drift` (or the existing precise structural/reference error when that is the actual cause). The error must not claim that a user accepted either version. The Router assesses substantive impact under section 1.2 before deciding whether to re-disclose and reconfirm before a new call.

## 4. Removed interfaces and compatibility

The following are removed, not deprecated compatibility interfaces:

- EventBus channel `pi-harness:plan-activation-v1`;
- activation request/context/result transport and Harness-owned disclosure helper;
- `PlanAuthorizationRegistry`, `PlanAuthorizationReceipt`, receipt lookup/insertion/integrity APIs;
- activation decision/outcome types, replay IDs, activation/decision timestamps, session-generation authorization state, and reset/restore/issuance logic; and
- receipt-specific `acceptance_required`, `receipt_corrupt`, and amendment/authorization response semantics.

No compatibility shim accepts, ignores, or translates the old activation payload; the completed repository-wide inventory found no direct consumer requiring one. A removed API has no migration period inside Harness; the migration is to ordinary Router confirmation followed by normal delegation.

`acceptance_required` has no remaining role in this boundary: absence of a receipt is no longer a state. Any unrelated use discovered by repository-wide search must be explicitly justified in the implementation review or removed; it must not be retained by habit.

## 5. Failure and session semantics

Malformed Handoffs, invalid Skills, unavailable or malformed candidates, legacy Role/modelRole configuration, unreadable references, invalid admission shapes, tuple mismatch, forbidden model or capability fields in the Handoff, and canonicalization failures retain precise structural/reference errors. Current-call authority or Plan drift fails closed. No failure mutates authorization state because no such state exists.

Reload, new session, resume, fork, shutdown, and session-generation changes do not clear or restore Harness authorization; there is nothing to clear or restore. No replacement marker, flag, audit event, confirmation token, persistence, or Host seam may be introduced.
