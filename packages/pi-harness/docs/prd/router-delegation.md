## Evidence-branch coordination outcome

A user may ask for one deliverable that depends on separately useful, independently verifiable evidence. The Router must retain the branches' distinct outcomes and truthful completion states while assembling the one requested deliverable only from evidence whose dependencies are satisfied. Independent ready branches should be able to make progress without waiting on an unrelated branch when the available delegation environment permits background overlap; tool calls need not be simultaneous. When that capability is absent or unknown, the Router must obey the effective backend contract and serialize or stop, without representing unverified work as complete.

Delegated units should have clear verification boundaries and the context needed to succeed with the least sufficient reasoning and impact requested separately. Splitting to lower a capability score, hiding consequential impact, or manufacturing valueless fragments is not an outcome. An implementation must preserve Router-owned coordination, exact per-Handler delegation, user authorization, and backend selection freedom; this documentation change does not claim that any installed tool now permits multiple same-turn launches.

## Preparation outcome

A user and Router must be able to delegate authorized work that is not bound to an executable Work/Plan/Waves graph, including read-only investigation, explicitly authorized PRD/ADR/Spec writing, initial Work/Context/Plan/Waves preparation, and a bounded independent change where applicable authority and authorization permit it. This standalone path replaces and expands the former atomic path; size, complexity, file count, or Skill name alone must not select admission. Planned work instead binds one selected executable tuple and retains its scope confirmation, dependencies, conflicts, and gate requirements. Missing implementation prerequisites must not be bypassed by relabeling work standalone.

Preparation is an effect category within standalone, with classification, admission selection, and decomposition owned by the existing `delegation-strategy` Skill. The Router retains authorization, roles, outcome/Result coordination, and on-demand loading; the Resolver checks shape, readable actual references, and exact invocation binding without deciding semantic effects or permission. Initial planning must use existing inputs and declare future outputs without requiring those outputs to be readable already.

Preparation must yield a bounded, verifiable result while preserving the separate implementation decision. Its allowed writes are explicitly authorized authority writing and initial derived-document preparation. It does not permit production code, configuration, dependency, lockfile, or LLM-instruction changes, runtime installation/reload/deployment, Git staging/commit/merge, or execution of the prepared plan. These preparation limits do not prohibit an independently authorized standalone change under its applicable rules. Accepted authority and completed preparation do not confirm an implementation scope; later implementation requiring a plan still needs substantive disclosure and explicit user confirmation. Existing authorized restoration, containment, behavior-neutral maintenance, and planned-work confirmation keep their own boundaries.

## Problem

A Pi main session needs to handle arbitrary user input without treating every request as immediate domain work. It must decide whether to respond directly or coordinate delegated work, select the Skills and model investment appropriate to that work, and retain control over the next step after a Handler returns.

## Product

`@settingdust/pi-harness` is a dedicated Pi package that replaces the default main-session system prompt with a Router prompt. The Router coordinates work; it does not perform project-domain reading, research, editing, execution, or independent verification itself. When delegation is needed, the Router builds a structured Handoff, selects one primary Skill and optional companion Skills, requests semantic non-negative integer `reasoning`/`impact` capabilities, and supplies the compatible registered delegate-tool name and startup parameters. The Resolver validates the request, resolves the exact invocation, launches through that selected tool, and returns resolution plus raw launch evidence without interpreting Handler Result business content or advancing work. The Router maintains a bounded, environment-adaptive main-session Todo projection for multi-step coordination: it uses available native task status and fields when they express the needed fact, otherwise it preserves the closest truthful native status and records partial, failed, blocked, conflict, and stale facts in existing descriptions, subjects, or ordinary Router coordination messages. It uses identity and visible fields/messages already available in the environment for correlation; it does not require persistent subagent identity or generation records, canonical Result digest storage, restart/outbox APIs, exact Todo description mutation, or matching native terminal states. If safe correlation or cleanup cannot be established, it retains the Todo and reports the limitation. Handler Results return to the Router, which alone interprets launch status/evidence, correlates the full Result, projects Todo and Waves state, checks completion evidence, and releases satisfied dependencies. Resolution success, a returned launch value, or terminal backend status alone must not become a work-completion claim.

Todo cleanup is part of the Router's main-session projection lifecycle under the [owning Spec](../spec/router-delegation.md#todo-cleanup-lifecycle) and [ownership decision](../adr/0001-router-resolver-handler-boundaries.md). After a complete correlated terminal Result is applied and the Router has completed the relevant gate and dependency judgment, the Router must actively inspect cleanup before handing off to another current outcome, waiting, stopping, or making the final report. It may remove only Todo records whose identity and required fields are clear and non-contradictory, whose Result and dependent decisions are complete, and which are neither current, active, nor unresolved. Current remains protected during verification, repair/review, related user decisions, or another coordination duty; after those duties are complete the Router may explicitly close or hand off that role, with necessary evidence retained, including before the final report. Cancellation or changed direction first requires accounting for active work and completed effects. Completion alone does not make a record removable. The Router must select an actually callable tool from its current schema, description, and known contract and must verify that the operation targets the intended record or safe set atomically while preserving every survivor's fields, order, and status. Proven eligible stable targets and a suitable tool require cleanup; a capability gap, unsafe concurrency, or uncertain target requires retention and a concrete explanation. A failed or unknown mutation result produces no automatic retry or cleanup-success claim; missing cleanup does not change an otherwise completed work Result. Group deletion requires every child and the container role to qualify, while a full clear requires the entire list to qualify with no survivors. Duplicate notifications must not repeat projection, release, or deletion of a newly created same-name record. Cleanup affects only Todos and preserves Results, sessions, manifests, and artifacts; it never uses `subagent_remove`.

## Outcomes

- Main-session responses can remain direct for clarification, summaries, completion, blocking conditions, and other work that does not need delegation.
- Delegations carry validated Skills, references, constraints, deliverables, semantic capability requirements, and a stable YAML handoff prompt; the Resolver selects the exact available provider/model/thinking candidate.
- Invalid Skill names, inaccessible referenced files, legacy or malformed candidate configuration, unavailable candidates, and insufficient capability prevent a Handler from starting.
- Handlers return a normalized YAML Result; the Router alone interprets and correlates it and selects subsequent work. `partial`, `blocked`, and `failed` remain distinct from `completed`; uncertain launch effects or unusable Result evidence leave the affected completion predicate unsatisfied without inventing a fifth Handler Result status. A single requested deliverable can depend on distinct evidence-branch Results without conflating branch failure, completion, or final delivery.
- Candidate capability investment is configurable per user without committing provider or account details to a project.

## Scope

The first package contains:

- an always-on extension that replaces Pi's default system prompt;
- the `resolve_delegation` tool with a runtime-generated schema;
- paired standalone/planned admission for work outside an executable graph and work bound to one selected tuple, with preparation classification and routing owned by the existing strategy Skill;
- a user-level nested candidate configuration UI opened by `/harness config`;
- a backend-neutral `handler` Agent definition;
- a complete initial library of 29 composable software-work Skills;
- a bounded Router-owned main-session Todo projection for multi-step coordination, with one item per independently observable outcome, environment-adaptive semantic status projection, and active cleanup only when the actual available tool can prove safe, atomic, lossless deletion;
- documentation for the Router, Resolver, Handoff, Result, capability candidates, Skill library, Todo lifecycle, backend adaptation, and configured delegate-tool launch contracts.

## Non-goals

The first version does not provide arbitrary-tool execution, tool-category inference, a delegate-tool registry owned by Harness, retries, fallback, subagent process lifecycle, worktrees, queues, cancellation, timeouts, automatic loop limits, persistent task ownership, conflict detection, or cross-provider fallback. It does not revoke Pi tools from the Router; Router restraint and semantic delegate eligibility are defined by its system prompt and operating contract.

The package does not depend on `pi-dust`, `pi-dust-harness`, or other reference projects. Those projects are design evidence only.

## Success Criteria

A configured user can install the package, start Pi, and have the Router reliably produce either a direct response or a resolver-validated delegation request. The Router can select package, user, and project Skills as per-Handoff primary and companion methods. A compatible backend can run the bundled Handler Agent through the Resolver's exact selected-tool invocation and make the full Result available to the Router without requiring a project-specific wrapper protocol. The [Backend Adaptation Spec](../spec/backend-adaptation.md) defines raw launch evidence; the [Router Spec](../spec/router-delegation.md#launch-evidence-and-router-progression) defines its Router-owned interpretation. Success requires preserving resolution rejection, launch failure or cancellation, uncertain effects, and each Handler Result status as distinct facts; only a safely correlated `completed` Result with the required evidence satisfies a completion predicate by default. For a shared deliverable with independent evidence branches, success also requires separately observable branch states, dispatch of ready nonconflicting branches when the effective backend permits overlap, and a final writer that consumes only satisfied dependencies. Lack of overlap support must not become a false completion or authorization claim.

Admission success additionally requires that authorized work outside an executable graph can use standalone without an artificial tuple prerequisite, even when its investigation is complex. An authorized first Work/Context/Plan/Waves outcome must use readable current inputs and declared future output targets without requiring those outputs to exist beforehand. Missing actual references, permission, or required implementation prerequisites still block the affected work. Preparation completion leaves implementation unstarted until its own authority and confirmation requirements hold. The [standalone and preparation acceptance scenarios](../spec/router-delegation.md#preparation-acceptance-scenarios) define observable checks for later implementation, not current runtime acceptance. The Spec also owns the atomic discriminator compatibility break and retention of the existing `invalid_atomic_basis` error name; no compatibility alias or new authorization follows from this product amendment.

Todo lifecycle success additionally requires an active pre-handoff, pre-wait, pre-stop, or pre-final-report cleanup check after each relevant complete Result and gate/dependency decision. The Router must prove cleanup eligibility from actual visible identity, fields, status, Result, and dependency state; completion alone is insufficient. It must choose a currently callable tool by its real schema, description, and known contract, preserve non-target records without loss, and treat a failed or unknown mutation result as unverified without automatic retry. Static prompt or Skill checks establish only the instruction ordering and prohibited boundaries. A real Router model execution must demonstrate target qualification, actual tool selection, atomic local deletion, survivor preservation, group deletion only when every child and container record qualifies, duplicate-notification safety, and retention with a concrete limitation when the tool cannot prove the contract.

## Capability Request Semantics

The Router must follow the independent-axis guidance and concrete examples in [Router semantics](../spec/provider-model-thinking-capability-selection.md#6-router-semantics). `reasoning` estimates correctness and verification work; `impact` estimates actual consequence. Each delegation requires fresh judgment of objective, ambiguity, reasoning needed for correctness, verification burden, and actual consequence, requesting the least sufficient finite non-negative integer on each axis. A high value on one axis does not imply a high value on the other; neither axis is a total score, weighted score, priority, or phase level.

Reasoning guidance is `0` for mechanical, clearly bounded, low-ambiguity work; `1` for a small settled implementation/check or simple state/documentation reconciliation; `2` for ordinary Plan/Tasks, independent review, or multi-file impact analysis; and `3` for final review involving architecture, security, migration, authority conflict, a complex root cause, or unusually difficult uncertainty. Ordinary Plan/Tasks and independent review normally require at least reasoning `2` because of synthesis or independent judgment, not their labels; simple mechanical reconciliation may still require only `1`, or `0` where actually sufficient.

Impact guidance is `0` for local, reversible work without external impact; `1` for one-module consequences; `2` for cross-module or material behavior/compatibility effects; and `3` for high-consequence, hard-to-reverse, security, data, or external-system risk. Planning or review does not by itself increase impact. `0..3` is common guidance, not a protocol range or upper bound. No Skill-name, document-type, or workflow-phase mapping, combined score, or automatic classifier is introduced.

Success requires the Router prompt to express these distinctions and examples while preserving Resolver selection and exact metadata forwarding; prompt-contract checks establish wording, not actual model classification.
