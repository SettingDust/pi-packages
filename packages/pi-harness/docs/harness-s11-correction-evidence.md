## Cause and correction

The original `s10-s11-change.jsonl` asserted that a reformatted Plan may not be the exact confirmed artifact and required refreshed confirmation for unchanged owner-only scope. This contradicts accepted Spec C5/C6/S11: byte drift can fail current-call legality, but only substantive change requires renewed approval. The same prompt gave the correct answer in the archived isolated drift case and its replay, and a fresh mixed-case replay before editing also answered correctly. Thus a deterministic runtime defect or a universally contradictory instruction is **not established**. The mixed fixture's "would have to" renderer also makes continued owner-only implementation potentially dependent on a new material dependency. One plausible instruction ambiguity was the Router prompt's unconditional sequence, "Select ... for each planned invocation, then obtain ... confirmation ... before delegation," which could be read as requiring confirmation per invocation despite its later unchanged-work rule. The actual cause of the original model's single bad decision cannot be isolated from model variability and fixture framing.

The minimal correction in `extensions/pi-harness.ts` ties the initial confirmation to the scope's first delegation, and makes byte-only retry explicit: compare current Plan with the confirmed scope and retry current-call validation against the current tuple without renewed confirmation. The adjacent `tests/extension.test.ts` assertions cover that wording. Material outcome, behavior, deliverable, architecture, consequential dependency, risk or verification changes still require confirmation of the affected portion. No Resolver or approval state changed.
