## Boundary and Order

1. **Authority prerequisite.** Reconcile `packages/pi-harness/docs/spec/router-delegation.md` sections 1 and 1.1 and the accepted direct-adaptation wording in `packages/pi-harness/docs/adr/0005-let-router-adapt-delegate-tools-directly.md`: establish visible outcomes before selecting a delegation; order identify/present, select, resolve and immediately delegate the exact invocation, then receive/project the Result before another decision. Resolve the Spec's *current* disjoint-input requirement against the approved candidate of shared read-only inputs for independent, nonconflicting work. Preserve serialization for shared writes, dependencies, ownership, authority, behavioral contracts and side effects; parallel execution still requires positively proven current Host capability, with serial fallback. Check `packages/pi-harness/docs/adr/0001-router-resolver-handler-boundaries.md` and `packages/pi-harness/docs/prd/router-delegation.md` for actual conflicting wording and reconcile only if necessary. The shared-read-only rule is **not yet normative**; stop before implementing it until accepted authority agrees. Do not promote ADR-0005's draft host-consumer amendment by implication.
2. **Execution tuple.** Derive `packages/pi-harness/docs/works/router-visible-outcome-workflow/tasks.md` from reconciled authority and this Plan; retain the existing `work.md`. Separate prompt/test implementation, behavioral verification and independent correctness review into independently reportable outcomes. The Router must disclose the exact Plan/Tasks and decision-relevant authority and obtain required current-user confirmation before planned delegation; document existence or the earlier design approval alone is not an admission receipt. These document writes and any overlapping authority writes serialize.
3. **Prompt and focused tests.** After step 1 and applicable step 2 authorization, reorganize `routerPrompt` in `packages/pi-harness/extensions/pi-harness.ts` into the four phases, using the existing Todo projection and semantic one-terminal-predicate rule. Update focused prompt-contract checks in `packages/pi-harness/tests/extension.test.ts`. Preserve closed Handoff/admission shapes, Router/Resolver/Handler ownership, `resolve_delegation` to `subagent_spawn` exact prompt/model/thinking forwarding, fixed `handler` agent, authorization and fail-closed Result/recovery duties. Do not add a dispatch gate, queue, wrapper, persistent task identity, protocol/Host change, backend work or deployment.
4. **Verify separately, then review independently.** Run the focused extension tests and package typecheck; inspect the produced prompt against reconciled authority. Exercise distinct behavioral traces for (a) three independent requests: three outcomes and three terminal states even if the final report is combined; (b) one bug: reproduce, diagnose, fix and internal check remain one outcome when they share one terminal predicate; (c) one comparison: alternatives and one recommendation remain one outcome; (d) independent writes to the same file: distinct outcomes, serialized execution; and (e) independent investigations sharing only read-only sources: concurrency only on positive Host capability, otherwise serial. Check phase ordering, truthful completed/partial/blocked/failed Todo projection before dependency release, conflict/replay fail-closed behavior and exact forwarding. Distinguish synthetic prompt-contract traces from observed live Router behavior; do not claim the latter from prompt text alone. Independent review checks authority correspondence, unintended scope expansion, failure/authorization paths and verification sufficiency on the same candidate bytes before completion is claimed.

## Risks and Rollback

The current Spec section 1.1 disjoint-input text and ADR-0001 non-conflicting-input text can cause a contradictory prompt if shared-read-only eligibility is implemented first; step 1 is a hard prerequisite. Prompt tests establish wording, not actual Router decisions or Host capability. On a failed review or behavioral check, keep prior accepted authority and runtime behavior in force, revise only the affected candidate documents/prompt/tests, and rerun affected checks and independent review; do not interpret a failed Result as completion, silently replay durable side effects, or alter unrelated/untracked files. No migration or persistent state transition is planned.
