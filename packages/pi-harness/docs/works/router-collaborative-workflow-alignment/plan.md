## Scope and outcome

One implementation scope aligns the Router's model-facing coordination instructions and the directly applicable planning/implementation Skill methods with C1-C10 and S1-S19. The result is a consistent decision sequence: settle material intent with the user before new normative behavior; derive a simple implementation Plan or, only for genuinely complex staged delivery, disclose and confirm an overview route first; disclose the ready implementation scope substantively and obtain explicit current-user confirmation before executing it; then refine Tasks, repair and verify within that confirmed scope without per-task confirmation. Stop and disclose material changes for renewed confirmation of the affected portion. Preserve the three narrow exceptions only under existing explicit authorization, with their verification and follow-on boundaries.

There is one reviewable Plan and one final instruction/contract-verification boundary. File count does not make this a complex staged delivery; creating a separate overview or route-confirmation step here would add no independently valuable outcome. [Tasks](tasks.md) decompose implementation internally, not into separate user approval gates or single-result Handler assignments. The Router still must decompose any later delegated work by independently observable result and decide continuation after each Handler Result.

## Tradeoffs and boundaries

The projection stays concise to avoid divergent duplicate authority, while the Spec remains the full decision contract. One Plan was sufficient because these coupled instruction/test edits shared one user-visible implementation scope and verification gate; if actual implementation had revealed independent stage outcomes or an unresolved material decision, the affected portion would have required a changed route/scope under C3/C6. No new approval registry, receipt, token, confirmation UI, backend/Host/Pi-core logic, runtime activation, migration, dependency, commit or deployment was part of this scope. The preparation-era pending implementation confirmation was superseded by the user's instruction to proceed after Router disclosure/start of the selected scope; the Work is not a confirmation receipt.
