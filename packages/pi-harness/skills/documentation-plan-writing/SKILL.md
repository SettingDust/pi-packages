# Documentation: Plan Writing

## Method

1. Read accepted PRD, ADR, Spec, Work Context, research, and current implementation evidence. Before deriving the Plan, consume a visible PRD/ADR/Spec assessment for every family: reuse (adequate coverage), update (same owner or decision identity needs amendment), create (missing required authority or distinct accepted ADR lifecycle), skip (no change needed or not applicable), or blocked (unresolved coverage, ownership, evidence, permission, or intent), with owning boundary, existing or intended path, and a one-sentence evidence-backed reason. Unknown ownership is unresolved; intended outputs are not readable references. Reuse reliable assessment covering current scope, decisions, owners, and relevant authority versions; material changes, contradictions, or important uncertainty require reassessment only of the affected portion. When authority is missing, false, materially incomplete, or subject to an important unresolved coverage question, load `spec-driven-development` through normal Skill loading as primary, companion, or a conditionally required method and stop affected planning with evidence and gaps for Router-owned communication. Required reconciliation must be complete before dependent planning; do not silently settle normative choices or record an unaccepted choice as an accepted ADR. Assessment supplies neither writing permission nor implementation confirmation.
2. State objective, scope, non-goals, assumptions, and authority references. Block when a material decision is unresolved.
3. Default to one coherent executable Plan for a simple deliverable, regardless of file count. For genuinely complex staged delivery, use an overview for stages, dependencies, and incremental outcomes; the Router confirms its route separately, without authorizing stage execution. Detail a ready stage when authority and evidence suffice; defer future detail only if it neither invalidates the route nor hides a current-stage decision. Identify each implementation Plan's Spec-derived scope and overview relationship, if any.
4. Describe the minimum strategy, affected ownership boundaries, data or control flow, migrations, and compatibility behavior. For a ready implementation scope include outcome and important exclusions, behavior or artifact changes and owners, steps and material dependencies, verification and completion criteria, and important tradeoffs, risks, and decisions. Paths or readiness text alone cannot replace Router disclosure and explicit current-user confirmation of that scope.
5. Sequence phases only where dependencies require them. Identify independent work and conditions preventing unsafe parallelism. Define verification for each material behavior and a final integration gate.
6. Include rollback, transition, security, observability, documentation, or release handling only when required by authority or risk.
7. Record risks and evidence-backed mitigations. Do not add speculative infrastructure or future flexibility.
8. For new `@settingdust/pi-harness` planned work, place Work, Context, Plan, and Waves in the same Work directory. Select one direct matching `plan.md`/`waves.md` pair or sliced pair under the Router Delegation Specification's grammar. Multiple pairs may share a Work; an overview name, status, or path does not authorize execution or infer selection. Link the Plan to its Work and exactly one Waves document; link Waves back to that same Plan and Work. State which Wave gates establish the selected Plan outcome.
9. Make the matched Waves document the sole executable graph, not a second decomposition in the Plan or a new `tasks.md`. Give every Wave and item a stable unique ID. Each Wave lists a non-empty set of item IDs, predecessor Wave gates, an incremental outcome, and a verifiable release predicate. Each item states bounded scope and effects, one observable completion predicate, required evidence, prerequisite item IDs, write ownership, and conflicts, with one Handler and one Result. Validate references, uniqueness, and acyclic dependencies; no gate may depend on itself. Serialize conflicting writes, ownership, authority, behavioral contracts, and side effects; shared read-only inputs do not conflict. Display order and Wave numbering create no dependencies or global barrier.
10. Release only explicit dependents after every required item is `completed` with its evidence and the gate checks pass; `partial`, `failed`, `blocked`, or a missing Result does not release them. The Router completely reads and reliably correlates full Results, communicates truthful facts through suitable runtime progress tools or ordinary messages under the effective tool contract, and judges release from item evidence and gate predicates independently of display success. Waves is not an automatic scheduler or an approval gate; confirmation remains Router-owned. Historical Tasks are compatibility records requiring explicit migration, never a Waves synonym or silent fallback.
11. The Router Delegation Specification owns tuple grammar and admission validation. This Skill's naming guidance, headings, links, and status text do not prove document kind or acceptance, and do not claim current runtime conformance.
12. Validate that every plan commitment derives from authority and that the Plan does not create new product or architecture decisions.

Settled evidence permits direct entry to a narrow owning writer without waiving assessment, authority, or authorization duties. SDD is not the exclusive ADR entrance or a mandatory reload at every stage or Handler call. Evidence-backed reuse or skip preserves authorized restoration/maintenance exceptions without a new ADR, Spec, Plan, or repeat approval of unchanged confirmed work. First Work/Context/Plan/Waves preparation uses standalone with current readable inputs and declared outputs, not the future tuple it creates; graph-bound implementation retains its confirmation, prerequisites, and gates. Methods serve only the current predicate: do not ask the user, dispatch, perform independent authority-writing outcomes, choose continuation, or advance Result/Waves/Todo state.

## Output

Report the Plan path, matched Waves path, strategy, dependencies, verification, risks, and blockers. Keep item-sized execution details in `waves.md`; use `documentation-tasks-writing` only for explicit historical migration compatibility.
