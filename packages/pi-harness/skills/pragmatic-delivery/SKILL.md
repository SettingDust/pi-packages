# Pragmatic Delivery

## Boundary

Apply this method on demand to the current Handoff's single terminal predicate, not as a persistent mode. Applicable authority, actual authorization, the Handler contract, and required checks (including fresh/current-call/JIT checks and completion evidence) take precedence. Skill loading, a Handoff, or Resolver acceptance grants no permission. Missing required Skills, references, permissions, decisions, or authority at entry means `blocked` without project work. Do not ask the user, delegate, take over sibling outcomes, select another stage, or advance Router-owned Todo/Waves/Result state; return evidence and gaps to the Router through the existing Handler Result.

## Method

1. **Reuse unchanged authority and authorization.** Continue only while existing authority and actual permission remain valid for the same scope and conditions. Do not invent repeat approvals for routine in-scope steps or turn research/review into implementation.
2. **Establish full responsibility and start directly.** Derive the deliverable, acceptance conditions, affected consumers, failure paths, and existing support commitments from context. After entry prerequisites hold, use suitable existing domain materials, methods, and tools first; for code, prefer project implementations, platform/standard-library features, or installed dependencies. Judge fitness by required behavior, failure handling, and state lifetime; proceed with a sufficient option instead of exhausting the ecosystem. Do authorized internal work within this predicate that does not depend on a later gap. Stop affected work and report the gap; use `partial` only for useful incomplete work actually done.
3. **Judge defenses by their practical effect.** For an added safeguard or step, identify what it detects and what its rejection, recovery, diagnosis, or decision changes. Add null checks, duplicate validation, guards, try/catch, fallback, compatibility, generalization, hashes, gates, freezes, or receipts only for explicit requirements, applicable contracts, or evidenced reachable failures. Trust validated internal contracts instead of rechecking them. Keep effective protection: real security/trust boundaries, authorization, data integrity, I/O failures, business invariants, and required recovery, compatibility, migration, and accessibility; lack of a production reproduction does not justify removing safety checks. Investigate an existing protection's relevant path when its role is unclear; missing evidence is not proof that it is unnecessary. Do not invent a consumer or verifier solely to justify a new optional manifest. Never swallow errors, silently fall back, or turn failure into success.
4. **Close concrete gaps locally and completely.** Expand the direct approach only for a supported input, consumer, failure, or obligation it does not cover. Complete necessary callers, data flows, contracts, tests, fixtures, and documentation within actual authorization; a larger necessary change is not scope creep, and an easier subset is not completion. Existing support commitments are current needs, not hypothetical flexibility. Reuse existing implementations, tools, and tests, not unrelated refactors or speculative abstractions/configuration. Preserve unrelated user edits without creating a freeze or hash ledger merely to prove preservation.
5. **Verify the actual domain question.** Choose and run the smallest sufficient check for the main failure and acceptance conditions, honoring mandatory checks. For code, cover affected behavior, failure handling, and state lifetime; broaden for public-interface or cross-module effects, not tests that merely restate low-impact implementation. For planning, check real dependencies, conflicts, gates, and executable acceptance criteria. Keep review read-only and test findings against connected behavior and failure paths. For research, match sources to the question, version, and conditions, and state evidence gaps. For documentation, check factual support, sources, conditions, and uncertainty. For numerical experiments check relevant error, convergence, boundaries, or baselines; file hashes do not establish algorithm correctness.
6. **Reuse still-valid evidence.** Reuse relevant checks while code, inputs, configuration, environment, and required freshness conditions remain covered. Repeat or expand for changes, failures, stale evidence, explicit requirements, or unresolved concrete questions, not ritual or a new evidence ledger.
7. **Distinguish blocks from safe correction.** Check whether a rule applies and authorization already covers the step; advice or personal caution is not an approval gate. On an ordinary in-scope failure, inspect the cause and completed or uncertain effects before correction. Permit a bounded correction or retry only within this same authorized outcome when repetition is safe and the cause can be addressed or new evidence supports retry. Unclear side effects or duplicate effects, missing permission, admission rejection, or required scope expansion stop affected work; cite the concrete rule/tool refusal and gap. Do not change paths to bypass rejection, repair configuration/environment without authority, or retry unchanged failures without new information. This grants no Handler continuation, resume, or dispatch and does not retry Resolver denial. Report checks not run or failed as such.
8. **Deliver when conditions hold.** Stop when the entire predicate is satisfied, necessary checks pass, and no known delivery-affecting issue remains. If unchanged state prompts repeated proof, stop that loop; do only necessary remaining work within this predicate or deliver, without extra proof bundles, frozen snapshots, or audit tasks. Report the result, necessary consequences, actual evidence, and material tradeoffs, gaps, and limitations through the existing Handler Result; keep `partial`, `failed`, and `blocked` distinct, never success. Preserve facts, sources, conditions, uncertainty, and unsuccessful or omitted checks when material to interpreting that result.
