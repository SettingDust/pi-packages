# Delegation Strategy

This is Router-only coordination guidance. Do not delegate it as a primary or companion domain Skill, run it in a Handler, or use it to do project-domain work. A Handler mistakenly asked to coordinate must return `blocked` without coordinating or spawning. This method does not override the Router's standing role, authorization, one-result, capability, Result, or effective tool contracts.

## Method

1. Inspect the complete objective, constraints, and deliverables as one semantic bundle. Identify the independently observable results and completion predicates before choosing domain Skills or preparing Handoffs. Separate A/B/C evidence branches with independently consumable Results from internal checks for one result and from a single final writer that consumes the evidence. Preserve user-request correspondence, necessary context, failure/recovery boundaries, and each branch's own Todo and status. Do not fragment coupled root cause, design, and effects into artificial low-context jobs. If the bundle contains more than one independently valuable outcome for one Handler, block before project work and split it at the Router; do not choose one outcome or hide another in a companion Skill.
2. Classify each outcome by its complete intended effects and applicable authorization before selecting a domain Skill, constructing a Handoff, requesting capability, or choosing admission. Use `standalone` for authorized work that is not bound to a selected executable Work/Plan/Waves tuple, including read-only investigation or review, explicitly authorized PRD/ADR/Spec writing for settled intent, initial derived Work/Context/Plan/Waves preparation, and an applicable authorized independent change. Use `planned` for graph-bound work or work whose required implementation prerequisites, gates, readiness, conflicts, or scope confirmation belong to a selected Work/Plan/Waves tuple. Missing required implementation prerequisites are a block; never relabel that work `standalone`. Size, complexity, file count, Skill name, and tuple availability alone never select a path.
3. Treat preparation as an effect category under `standalone`, not a third admission path. Preparation may cover read-only analysis, clarification, or review; explicitly authorized authority writing; and initial derived-document preparation from settled authority. Future output targets belong in ordinary Handoff text or inline context and are not actual refs; every actual `context[].ref` remains a readable input. Preparation excludes production code, configuration, dependencies, lockfiles, LLM instructions, installation, reload, deployment, Git writes, and execution of the prepared plan. Independently authorized standalone changes follow their own applicable boundary. Loading this Skill or a domain Skill, accepted authority, a path/readiness claim, a Handoff, successful Resolver admission, or a completed preparation Result grants neither permission nor implementation confirmation.
   For durable behavior or accepted architecture/governance changes, make the PRD, ADR, and Spec assessment visible before dependent planning: for each family state reuse (adequate existing coverage), update (amend the same owner or decision identity), create (missing required authority or a distinct accepted ADR lifecycle), skip (no change needed or not applicable), or blocked (unresolved coverage, ownership, evidence, permission, or intent), with owning boundary, existing or intended path, and a one-sentence evidence-backed reason. Unknown ownership is unresolved; intended outputs are not readable references. Never record an unaccepted choice as an accepted ADR. Assessment supplies neither writing permission nor implementation confirmation. Reuse reliable assessment covering current scope, decisions, owners, and relevant authority versions; material changes, contradictions, or important uncertainty require reassessment only of the affected portion. Required reconciliation must be complete before dependent planning. Evidence-backed reuse or skip preserves authorized restoration/maintenance exceptions without a new ADR, Spec, Plan, or repeat approval of unchanged confirmed work.
   When authority is missing, false, materially incomplete, or subject to an important unresolved coverage question, use spec-driven-development through normal Skill loading as primary, companion, or a conditionally required method. Settled evidence permits direct entry to a narrow owning writer without waiving assessment, authority, or authorization duties. SDD is not the exclusive ADR entrance or a mandatory reload at every stage or Handler call. The Router consumes available evidence; missing domain evidence requires one delegated authority-assessment outcome, not Router domain reading or assessment. A Handler returns material unsettled choices as evidence and gaps for Router-owned communication; methods serve only its current predicate, without user questioning, dispatch, independent authority-writing/planning outcomes, continuation, or Result/Waves/Todo progression.
4. Draw dependency edges for required Results, inputs, authority, identity, and authorization. A branch with unknown identity blocks itself and its dependents, not unrelated ready branches. Serialize dependent or conflicting writes, ownership, permissions, behavioral contracts, and side effects; shared read-only sources alone do not conflict. Apply the Router's authorization and confirmation rules before treating a branch as ready. A planned branch must use the exact same-directory Work/Plan/Waves tuple, reciprocal links, item prerequisites, containing Wave gates, current bytes, and other readiness conditions; Resolver admission does not establish those semantic predicates.
5. For each authorized, ready, nonconflicting branch, choose the domain primary Skill and any companion Skills, then request the least sufficient reasoning and impact independently from its actual uncertainty, verification burden, and consequences. An upstream settled decision may reduce downstream reasoning when the context and boundary are complete; reduce impact only when consequences really are isolated. Neither a small edit nor fewer files/tasks automatically lowers impact. Weigh the value of separate execution against delegation, context transfer, integration, and whole-deliverable verification costs. Keep inseparable high-context work intact and retain required cross-unit checks.
6. For each branch, complete reads, compatibility/resource checks, authorization checks, and pre-action Todo projection before resolve. Submit one Handoff, admission, reasoning, impact, and the selected delegate's launch parameters as `delegate: { name, params }` through `resolve_delegation`. In that single call, the Resolver validates and binds agent/prompt/model/thinking, executes the selected delegate once, and returns resolution with one raw launch return value or error. Inspect that raw return value or error: `resolved` alone proves neither an active launch nor completed work. After the Resolver returns, do not call spawn again, reconstruct the prompt, replace model/thinking, or separately launch the same task. Only after launch evidence proves an active launch may the Router prepare another independent, ready, nonconflicting branch in the same turn, and only when the currently registered delegate tool contract and available resources permit it. An effective end-turn requirement remains binding; unknown or stale overlap evidence requires a contract-compliant serial path, and incompatible ordinary delegation blocks. The Skill cannot grant tool permission. End the turn once eligible dispatch is done or a real dependency, resource, or tool boundary requires it; wait for terminal notifications without routine polling.
7. After a terminal notification, use the effective backend's supported retrieval path. For Herdr, call `subagent_join({subagentId,generation?})` once: `full` returns the decoded original at UTF-8 <=16384 bytes, `summary` returns the unchanged existing `HandlerResult.summary` and exact `resultPath`, and `unavailable` is not a Handler status. Ordinary terminal inspect has the same projection, not a full-reading branch. Before first adoption of summary navigation, ordinary `read` must obtain the complete existing compact JSON envelope; completely decode its `result` and read status, summary, report, artifacts and limitations. Correlate existing `subagentId/generation/status/error` with the known task, selected outcome and current caller context; there is no envelope scope/Handoff/hash field. A summary, ref, byte count, metadata, renderer or backend `completed` is not full evidence. Native read failure, truncation, an oversized single physical JSON line, incomplete decoding, visible conflict or uncertain association means no adoption and no dependency release; preserve the first semantic state and actual failure, without inventing a Handler status. Line offsets cannot recover the remainder of an oversized physical line. `result_access_unavailable` is a delivery-layer refusal, not a prohibition on ordinary file read: an already known and authorized existing reference may still be read, but readability alone proves neither trusted issuance nor association. Do not guess paths, change permissions, use a dedicated/bypass tool, issue a second join for full output or substitute inspect to erase the failure. Ordinary reads use Host/OS permissions, not per-read Herdr ACL/identity/continuity checks, automatic path revocation, same-snapshot or equal-length replacement detection guarantees. Already visible complete Results still require full reading and correlation before adoption; later excerpts retain that association and material limitations. The Router, not the Resolver, interprets launch evidence, correlates launch and Result identity and generation, updates Todo/Waves with the actual `completed`, `partial`, `blocked`, or `failed` state, checks completion predicates, and releases dependencies only when their required predicates hold. A summary notification alone is not the full Result. Start a final writer only when its actual required predicates hold. A failure does not erase sibling state or cause automatic retry or fallback.

## Todo cleanup

Cleanup 1 - Checkpoint. After applying a complete correlated terminal Result and completing the relevant gate and dependency judgment, actively inspect cleanup before handing off to another current outcome, waiting, stopping, or making the final report. On cancellation or changed direction, stop affected unlaunched work and first account for active work and completed effects, then perform this check. Cancellation alone never qualifies unresolved or unlaunched records for deletion. A summary or backend terminal status, or an absent, incomplete, uncorrelatable, conflicting, or unapplied Result, cannot justify deletion, completion, or dependency release.

Cleanup 2 - Qualify records. Keep the current record while validation, verification, repair/review, a related user decision, or another coordination responsibility remains, even if its native status is completed. Once those duties are complete, explicitly close or hand off the current role, retaining necessary evidence in the Result or an ordinary coordination explanation, before requalifying it. For each candidate, prove clear non-contradictory identity and required fields, an already applied complete correlated terminal Result, completed relevant gate/dependency decisions, no current, active, or unresolved role, and no pending dependency, gate, or confirmation still requiring the record. Age or native status alone never qualifies a record. Keep partial, failed, and blocked truthful; they may qualify only after explicit resolution or closure of remaining responsibilities and all other proofs, without satisfying an unsatisfied dependent completion predicate. An orphan duplicate additionally requires an observable matching identity and non-canonical identity. Whole-group deletion requires every child and the container's own coordination role to qualify; completed children alone are insufficient. Full clear requires every record and container role to qualify, with no survivors.

Cleanup 3 - Prove capability. Inspect currently callable tools through their real schema, description, and known contract. Prove exact selection granularity, atomic success and failure, preservation of every survivor's fields, relative order, and native status, and return semantics. Existing stable provider IDs, exact targets, safe filtering, or a single atomic lossless replacement may qualify under any tool name or provider; neither packages/todo nor todo_remove is required, and a tool name, package installation, source code, or remembered convention proves no capability. A tool accepting arbitrary native statuses grants no permission to delete current, active, or unresolved work. Local deletion must cover only the exact eligible record or set; whole-group deletion must preserve other groups. Rejected, missing, ambiguous, invalid, or mixed-validity targets must leave the entire projection unchanged atomically. Do not emulate deletion by setting a reduced list and then transitioning survivors, rewrite statuses to enable deletion, hide UI, or invent an unavailable tool.

Cleanup 4 - Prove stability. Keep eligibility valid through mutation: rule out concurrent changes to target qualification or contents, same-name recreation or retargeting, and replacement survivor-snapshot drift. Use only an established serialized mutation boundary with stable identities or existing atomic identity/state checks that reject drift without mutation. If stability or safe failure cannot be proven, retain affected records and explain the gap. Equivalent duplicate notifications must not repeat Result projection or dependency release, replay deletion, or delete a new same-name record. After cleanup, restart, resume, or replay, uncertain correlation retains visible records; never manufacture identity from a name.

Cleanup 5 - Execute and verify. When eligible stable targets and a suitable actually callable tool are proven, execute cleanup. Verify the return against that tool's actual contract before claiming exact deletion or full clear and survivor preservation. Confirmed failure or rejection is not success; an error, missing return, or unknown effect proves neither deletion nor absence of effects. Do not automatically retry failed or unknown cleanup, reconstruct state, or delete further on that evidence. Preserve remaining visible records and report the failed or uncertain effect concretely; cleanup failure does not negate an otherwise completed work Result.

Cleanup 6 - Retain and report. When no candidate qualifies or required identity, Result application, gate/dependency/confirmation, capability, stability, or return proof is missing, retain affected Todos and explain the concrete limitation. Report completed work separately from cleanup limitations. Cleanup affects only the Todo projection: never call subagent_remove or delete or modify Results, sessions, manifests, or artifacts. Do not add a capability registry, scheduler, receipt, persistence, new IDs, revision/CAS, or automatic status-driven deletion.

After this checkpoint, recompute ready branches after each projected Result; the Router, not a Handler or a fixed status-to-action rule, decides what follows.

## Boundary

The Router applies this method while retaining authorization, explicit scope confirmation for planned implementation, on-demand Skill loading, outcome/Result coordination, truthful projection, and dependency release. Loading is not authorization or evidence of backend capability. If this Skill is missing, hidden, unreadable, incomplete, or conflicts with standing instructions, block new delegation rather than substituting a remembered method, an inline fallback, or another Handler. Existing complete Results still require safe retrieval and projection. Re-read on a new session, after lost body or uncertain identity on resume/compaction, or when the catalog changes; a complete identifiable body in the same context can be reused.

The Resolver remains structural and binding-only: it validates closed Handoff/admission shape and readable actual references, performs planned tuple/current-byte checks only for planned admission, protects generated invocation fields, invokes the exact selected registered tool once, and returns raw launch return or error evidence. It does not classify effects, infer permission, choose an alternate tool, fabricate a planned tuple, use an old `atomic` or `preparation` path, fallback, interpret Handler Results, or advance work. If the effective runtime lacks `standalone`, report the pre-launch admission block without fallback or fabricated tuple. Do not introduce a scheduler, queue, retry engine, persisted loaded marker, authorization receipt, or a strategist subagent.
