# Delegation Strategy

This is Router-only coordination guidance. Do not delegate it as a primary or companion domain Skill, run it in a Handler, or use it to do project-domain work. A Handler mistakenly asked to coordinate must return `blocked` without coordinating or spawning. This method does not override the Router's standing role, authorization, one-result, capability, Result, or effective tool contracts.

## Method

1. Identify the independently observable results and completion predicates before choosing domain Skills or preparing Handoffs. Separate A/B/C evidence branches with independently consumable Results from internal checks for one result and from a single final writer that consumes the evidence. Preserve user-request correspondence, necessary context, failure/recovery boundaries, and each branch's own Todo and status. Do not fragment coupled root cause, design, and effects into artificial low-context jobs.
2. Draw dependency edges for required Results, inputs, authority, identity, and authorization. A branch with unknown identity blocks itself and its dependents, not unrelated ready branches. Serialize dependent or conflicting writes, ownership, permissions, behavioral contracts, and side effects; shared read-only sources alone do not conflict. Apply the standing authorization and confirmation rules before treating a branch as ready.
3. For each genuine bounded unit, choose the domain primary Skill and any companion Skills, then request the least sufficient reasoning and impact independently from its actual uncertainty, verification burden, and consequences. An upstream settled decision may reduce downstream reasoning when the context and boundary are complete; reduce impact only when consequences really are isolated. Neither a small edit nor fewer files/tasks automatically lowers impact. Weigh the value of separate execution against delegation, context transfer, integration, and whole-deliverable verification costs. Keep inseparable high-context work intact and retain required cross-unit checks.
4. For each authorized, ready, nonconflicting branch, complete reads, compatibility/resource checks, and pre-action Todo projection before resolve. Resolve one Handoff and immediately launch that exact resolved invocation as the next environment action. Never batch resolves before launches or insert another action between a successful resolve and its spawn. After an active launch, prepare another independent ready branch in the same turn only when the currently registered delegate tool contract and available resources permit it. An old end-turn rule remains binding while effective; unknown or stale overlap evidence requires a contract-compliant serial path, and incompatible ordinary delegation blocks. The Skill cannot grant tool permission. End the turn once eligible dispatch is done or a real dependency, resource, or tool boundary requires it; wait for notifications without routine polling.
5. Obtain the full Result through the backend's supported retrieval path after a summary notification, correlate it and project its actual `completed`, `partial`, `blocked`, or `failed` state before reconsidering dependencies. Start a final writer only when its actual required predicates hold. A failure does not erase sibling state or cause automatic retry. On cancellation or changed direction, stop affected unlaunched work and account for active tasks and completed effects. Recompute ready branches after each projected Result; the Router, not a Handler or a fixed status-to-action rule, decides what follows.

## Boundary

Loading is not authorization or evidence of backend capability. If this Skill is missing, hidden, unreadable, incomplete, or conflicts with standing instructions, block new delegation rather than substituting a remembered method or another Handler. Existing complete Results still require safe retrieval and projection. Re-read on a new session, after lost body or uncertain identity on resume/compaction, or when the catalog changes; a complete identifiable body in the same context can be reused. Do not introduce a scheduler, queue, retry engine, persisted loaded marker, or a strategist subagent.
